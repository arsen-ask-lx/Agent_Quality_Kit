# Цвет приходит из токена темы, а не литералом в компоненте

**Намерение.** Литеральный цвет тема не перекрашивает. В проекте с несколькими темами экран,
свёрстанный литералами, в тёмной теме остаётся светлым пятном — и видит это не автор, а
пользователь, который тему переключил. Дефект тихий по построению: в теме автора всё правильно.

**Какой отказ это поймало.** Живой проект на React с двенадцатью темами. Запрет на сырой цвет
там оказался проверкой №8 из семнадцати в собственной оснастке — и завели его не из вкуса, а
после экранов, не переживших переключение темы. Запись в журнале: `incidents/README.md`,
2026-09-06, там же измерено соотношение, ради которого запись переносили в каталог: из тридцати
с лишним запретов интерфейса машина ловила одиннадцать, остальные держались на глазах человека.

**Файл-источник значений называет проект.** Где-то литерал обязан быть — иначе токену неоткуда
взяться. По умолчанию проверка пропускает файлы, чьё имя содержит `tokens`, `theme`, `palette`,
`colors`, `variables`, `design-system`. Своё имя проект называет сам, рядом с командой в
манифесте — тем же приёмом, что каталоги с законной печатью в `no-print-in-prod`:

```yaml
color-from-token: "AQK_COLOR_SOURCE='tokens|brand' bash .aqk/gates/color-from-token/check.sh ."
```

**Готовый аналог есть, но он покрывает меньше, и поэтому его здесь нет.** У `stylelint` есть
правило `color-no-hex`, и для файлов стилей оно точнее нашего поиска. Но оно видит только стили,
а литерал в компоненте — `style={{ background: "#2563EB" }}`, `className="bg-[#2563EB]"` —
остаётся вне его. Родной рецепт покрывал бы половину предмета, и запись означала бы разное в
зависимости от того, что стоит в системе. Урок этого же дня: родной и переносимый рецепты одной
записи обязаны мерить одно и то же. Поэтому рецепт один, переносимый; кому нужна точность по
стилям — ставит `stylelint` отдельно, это не отменяет запись.

**Замер на живом проекте.** React, двенадцать тем, 2750 файлов кода. Первый прогон дал 20
находок, и **все 20 были чужими** — литералы в отдельных html-документах внутри `.claude/`:
отчёты и справочники оснастки агента. Отдельный html-документ темы не имеет и иметь не может,
литерал там законен; `.html` убран из списка расширений — не на вкус, а по этому замеру.
Второй прогон: одна находка во фронтенде — палитра диаграммы загрузки, где цвета треков вписаны
литералами Tailwind-500 и потому не меняются вместе с темой. Ложных срабатываний: **одно**, и
оно тоже исправлено — цвет, упомянутый внутри многострочного комментария, читался как находка.

**Чего НЕ ловит.**

- Цвет, собранный по частям: `"#" + hex`, `rgb(37, 99, 235)`, `hsl(...)`, именованные `red` и
  `white`. Проверка ищет литерал в форме `#rgb`, `#rrggbb`, `#rrggbbaa`, а не «цвет вообще».
- Селектор по идентификатору, записанный шестнадцатеричными буквами (`#abcdef { … }`), и якорь
  в ссылке той же формы читаются как цвет. Это цена простоты; лечится именем в allowlist.
- Литерал в разметке и в документации: расширений `.md` и `.html` в списке нет намеренно.
  В разметке цвет упоминают, а не применяют; отдельный html-документ не имеет темы, и литерал
  в нём законен — как печать в скрипте для `no-print-in-prod`.
- Цвет, вычисленный в рантайме: `lighten(base, 0.2)`, значение из ответа сервера, инлайн-стиль,
  собранный из переменной. Проверка читает исходник, а не то, что окажется в браузере.

**Образцы.** `red/` — три стека, где цвет вписан литералом: React со `style`, обычный CSS,
однофайловый компонент Vue. `green/` — то же самое через токены, плюс `tokens.css`, где литерал
законен, и заметка в разметке, на которой проверка обязана молчать.
