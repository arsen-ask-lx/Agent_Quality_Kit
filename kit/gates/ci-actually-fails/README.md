# Проверка в конвейере может провалиться

**Намерение.** Шаг выполнен, круг зелёный, проверка не сработала. `run: pytest || true` —
это строка в логе, а не проверка.

**Какой отказ это поймало.** Дыру нашли у себя. Запись `gates-run-in-ci` отвечает на вопрос
«упомянут ли гейт в конфиге конвейера» и на этом останавливается — то есть конфиг с
`run: pytest || true` проходил её зелёным. «Упомянут» и «работает» — разные утверждения, и весь
этот стандарт стоит на том, чтобы их не путать; у себя мы их спутали.

Замер по пятнадцати чужим репозиториям подтвердил, что класс живой: у `reviewdog` два шага с
его собственными линтерами идут под `continue-on-error: true`. Запись в журнале:
`incidents/README.md`, 2026-09-06.

**Что именно проверяется.** Конфиг разбирается по шагам. Шаг красный, если он **и** выносит
вердикт, **и** не может провалиться.

| Выносит вердикт, если | Не может провалиться, если |
|---|---|
| команда есть в списке запускалок (`pytest`, `eslint`, `go test`, `golangci-lint`, `mypy`, `cargo clippy`, …) | шаг помечен `continue-on-error: true` |
| команда объявлена гейтом в `.aqk.yml` **этого** проекта | задача помечена `allow_failure: true` (gitlab) |
| в **имени шага** стоит слово `lint`, `test`, `check`, `verify`, `audit`, `scan`, `coverage` | провал погашен в самой команде: `\|\| true`, `\|\| :`, `\|\| exit 0` |

Гашение прямо в команде красится только для закрытого списка запускалок: `docker network create … || true` — это идемпотентность, а не выключенная проверка.

**Труба после проверки — третья форма гашения (GitHub Actions).** `run: pytest | tee test.log`
выходит кодом `tee`, то есть нулём, даже когда тесты упали. Документация GitHub Actions, таблица
оболочек по умолчанию: шаг без `shell:` на Linux идёт как `bash -e {0}` — без `pipefail`; явный
`shell: bash` — как `bash --noprofile --norc -eo pipefail {0}`. Проверено вживую: `false | tee`
под `bash -e` даёт 0, под `-eo pipefail` — 1. Красится, когда перед трубой **на месте команды**
стоит запускалка (`pytest`, `npx vitest run`, `cd web && npm test`), труба вне кавычек, и код
трубы ничем не спасён. Спасают: `shell: bash` у шага, `defaults: run: shell: bash`,
`set -o pipefail` до трубы, `exit ${PIPESTATUS[0]}`, Windows без своей `shell:` (там pwsh,
который выходит по коду нативной команды).

Откуда: доклад С. Шимы «AI-кодинг, не вайб-кодинг» (2026-09-19), правило гейта «пайп
запрещён» — у автора так красный тест уехал на прод. Эта запись на той же строке молчала.
Замер 2026-09-21 по 49 чужим конвейерам (267 файлов, репозитории с коммитами Claude): первая
версия, искавшая имя инструмента где угодно в строке, дала 7 срабатываний, из них 6 ложных —
`gitleaks` в адресе `curl … | tar` (трижды), `Trivy` в тексте JS-скрипта, путь в `echo "$FILES" | grep`,
`-g '5368|6428'` в кавычках.
После сужения — одно: `npm run test:coverage:merge | tee coverage-output.txt` в `untangle`, где
следующие строки проверяют только процент покрытия, а упавшие тесты проходят. Все четыре
ложные формы закреплены зелёными случаями в `tool/selfcheck/smoke/ci-pipe.test.mjs`.

**Хук husky — тот же вердикт, вынесенный раньше конвейера.** `pnpm lint-staged || true` в
`.husky/pre-commit` пропускает коммит с любым нарушением. Смотрятся только блокирующие хуки
(`pre-commit`, `pre-push`, `commit-msg` и родственные): код выхода `post-merge` и прочих `post-*`
git не читает. Внутренности `.husky/_/` — не хуки проекта. `|| true` гасит всю цепочку `&&` перед
собой, поэтому `yarn lint:fix && git add -A || true` — тоже гашение. Прощается только вывод в
ФАЙЛ, который следом сверяют: в хуке «после гашения есть ещё команда» ничего не значит — у
`npm run lint:dependencies || true` следом шла сборка.

Откуда: на близнецах 2026-09-21 `|| true` в husky не поймали ни AQK, ни `code-quality-skill`,
назвал его только Exadel. Замер 2026-09-22: поиск GitHub `"|| true" path:.husky` — 4416 файлов;
из 97 хуков (по одному на репозиторий) проверку гасят 7 у пяти авторов — `pnpm lint-staged`,
`npx --no -- lint-staged 2>/dev/null`, `npx --no -- commitlint --edit ${1}`, трижды
`npm run lint:dependencies`, `yarn lint:fix && git add -A`. Первая версия, искавшая имя
инструмента где угодно в строке, покрасила ещё два — `$eslint_out` в имени переменной и
`\.gitleaks\.toml$` в шаблоне `grep`; после правила «запускалка на месте команды» — ровно семь из
семи, ноль ложных, под gawk и под mawk. То же правило теперь у ветки `|| true` в конвейере: она
красила диагностику `ls "${PLAYWRIGHT_BROWSERS_PATH:-/ms-playwright}" || true` (замер по 64 чужим
конвейерам). Случаи — `tool/selfcheck/smoke/ci-hooks.test.mjs` и `ci-pipe.test.mjs`.

**Готовый аналог.** Не нашли. [`actionlint`](https://github.com/rhysd/actionlint) разбирает
синтаксис workflow, [`zizmor`](https://github.com/woodruffw/zizmor) ищет в них дыры
безопасности — ни тот, ни другой не спрашивает, может ли шаг провалиться. `continue-on-error`
для них — законная настройка, каковой она и является: незаконной её делает то, ЧТО под ней
стоит, а это знает только проект.

**Исход переспрашивают — маска законна.** `continue-on-error` иногда стоит не ради прощения
провала, а чтобы дать выполниться шагам ПОСЛЕ проверки; вердикт выносится отдельным шагом
`if: steps.<id>.outcome == 'failure'` → `exit 1`. Так устроен `pre-commit.yml` в `fastapi`:
проверка идёт под маской, потом чинит файлы и пушит их в ветку, и только в конце роняет
сборку. Такой шаг больше не находка. Условие узкое: в файле должна быть И ссылка на исход,
И падение — переспросить исход и ничего с ним не сделать значит простить провал длиннее на
три строки, и это по-прежнему красное (образец `red/.github/workflows/soft.yml`).

Замер 2026-09-07 по пяти чужим репозиториям: молчал на всех пяти. На `fastapi` — по
случайности, слово-примета не совпало с именем шага «Run prek - pre-commit»; назови они его
«Run lint», гейт покрасил бы законный уклад. Дефект найден разбором молчания, а не находки.

**Чего НЕ ловит.**

- **Проверку, которую не по чему опознать.** Задача `mutation-diff` с именем «Mutation score on
  changed files» под `continue-on-error` (нашлась в `kodus-ai`, автор сам пометил её «advisory —
  does not block») не опознаётся: в имени нет слова-приметы, а команда не из списка. Объяви такую
  проверку гейтом в `.aqk.yml` — тогда она станет видна точно, а не по догадке.
- **Провал, погашенный внутри скрипта.** `set +e`, `trap`, `exit 0` в конце `run: |` — это уже
  логика скрипта, а не конфиг конвейера.
- **Шаг, который проходит по другой причине.** Тест, всегда возвращающий 0, — не эта запись,
  а `test-has-assertion`.
- **`if: always()`** маскировкой не считается: он про порядок выполнения, а не про вердикт.
- **Хуки не husky.** `lefthook.yml`, `.pre-commit-config.yaml`, `.githooks/` не разбираются —
  замер был только по husky. И запись показывается проекту с конвейером: условия складываются по
  И, а признака «есть хуки» у осмотра нет, так что проект с husky без конвейера её не увидит.
- **Сборку, принятую за проверку.** Шаг под `continue-on-error` красится, если в нём звучит имя
  из списка: необязательная сборка плагина `gradle … buildPlugin` в релизе красится, хотя
  вердикта не выносит (`Cyapow/plumb`, замер 2026-09-22). Сужение этой ветки не мерено.
- **Трубу вне GitHub Actions.** Оболочку по умолчанию GitLab и CircleCI мы не сверяли, поэтому
  там труба не красится: молчать честнее, чем гадать.
- **Трубу, спасённую позже по-другому.** Если после `pytest | tee log` скрипт сам разбирает
  журнал и падает на провале, гейт этого не узнает и покрасит шаг. Средство — `set -o pipefail`
  в начале: оно не мешает разбору журнала.
