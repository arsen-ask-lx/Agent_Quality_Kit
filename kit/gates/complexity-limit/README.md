# Функция не вырастает до сложности, в которой её нельзя удержать в голове

**Намерение.** Ограничить сложность одной функции: сколько в ней ветвлений, инструкций и
уровней вложенности.

**Какой отказ это поймало.** Ревизия гейтов в `audit_project` показала: **сложность функций не
мерил никто**. Нашлось 75 функций сложнее нормы, худшая — с **29 ветвлениями**, и лежала она в
контуре проверки целостности файлов. Запись в журнале: `incidents/README.md`, 2026-08-27.

**Почему машина, а не внимательность.** Сложность растёт по одному условию за раз. Ни одна
правка не выглядит как «пора выделять функцию», а момент, когда стало поздно, проходит незаметно.
Для агента это дороже, чем для человека: в таком месте он начинает переписывать вместо правки.

**Готовый аналог есть, и он точнее.** В Python это `ruff --select C901,PLR0912,PLR0915`:
цикломатическая сложность, число ветвлений, число инструкций. В TypeScript — правила `complexity`
и `max-depth` в eslint. Рецепты под эти стеки берут готовое.

**Переносимая проверка грубее, и это признаётся.** Она меряет только **глубину вложенности** —
косвенный признак: функция может иметь двадцать ветвлений подряд без единого вложения и проверку
пройти. Она для стеков, где готового инструмента нет, а не замена ему.

**Разметке предел мягче.** В `.jsx`, `.tsx`, `.vue` и `.svelte` пять уровней вложенности — это
обычная вёрстка, а не сложная логика. Там предел выше на три. Без этой поправки проверка краснела
на нормальных компонентах живого проекта — шесть находок из девяти были именно такими.

**Предел настраивается** переменной `AQK_MAX_DEPTH`, по умолчанию пять уровней.

**Тяжёлая проверка.** На проекте в четыре тысячи файлов — около семи секунд. Место такой
проверки — перед пушем и в конвейере, а не на каждый коммит: гейт, который заставляет ждать,
начинают обходить.

**Образцы.** `red/` — восемь уровней вложенности. `green/` — тот же смысл, разбитый на две
функции с ранним выходом.
