# У спецификации API есть арбитр

**Намерение.** `openapi.yaml` — это обещание чужому коду: вот поля, вот типы, вот что
обязательно. Обещание, которое никто не сверяет с сервером, расходится с ним молча и
обнаруживается у потребителя. Наш центральный класс, только на уровне API.

**Какой отказ это поймало.** Стенд 2026-09-09: сервер отдаёт `id` строкой вместо числа,
обязательного `email` не отдаёт вовсе, `created_at` — не дата. Пятисоток при этом нет, коды
ответа честные. Кто что сказал на одной и той же паре «спецификация + сервер»:

| Инструмент | Код возврата | Что сказал |
|---|---|---|
| `spectral` (набор `spectral:oas`) | **0** | нет контакта, нет описания, нет тегов |
| `schemathesis`, умолчания | **1** | три нарушения схемы в ответах |
| `schemathesis -c not_a_server_error` | **0** | «18 из 18 прошли» — ни одной находки |

Отсюда обе красные ветки. Замер целиком — `incidents/README.md`, 2026-09-09.

**Что именно проверяется.** Записи две, и вторая тоньше первой.

1. **Спецификацию не держит ни одна команда.** Файл `openapi*.{yaml,yml,json}` (и `swagger*`,
   `asyncapi*`) в репозитории есть, а ни в конвейере, ни в сборочных файлах, ни в скриптах, ни
   в объявлении пакета нет ни одного инструмента из четырёх семей ниже.
2. **Арбитр сужен до «не пятисотка».** `schemathesis --checks not_a_server_error` (или `-c`).
   У `schemathesis` по умолчанию включены **все** проверки, включая
   `response_schema_conformance`; сужение до одной — не настройка, а отключение.

Четыре семьи держателей отвечают на **разные** вопросы, и подменять один другим нельзя:

| Семья | Инструменты | Вопрос |
|---|---|---|
| сверка с сервером | `schemathesis`, `dredd`, `portman`, `newman`, `pact` | документ не врёт? |
| линт документа | `spectral`, `redocly`, `vacuum`, `openapi-spec-validator`, `swagger-cli` | документ хорошо написан? |
| ломающие правки | `oasdiff` | вчерашний клиент переживёт сегодняшний выпуск? |
| потребитель | `openapi-typescript`, `orval`, `oapi-codegen`, `openapi-generator`, `kubb` | типы порождены договором, а не переписаны руками? |

**Готовый аналог.** Не нашли, и это проверено. Все четыре семьи предполагают, что их **уже
запускают**: `spectral` читает документ, `schemathesis` — сервер, `oasdiff` — две версии
документа. Ни один не задаёт вопрос «а меня вообще кто-нибудь запускает». Это ровно форма
записи `promise-has-gate`: обещание, у которого не назван сторож.

**Чего НЕ ловит.**

- **Что арбитр проверяет ПРАВИЛЬНЫЕ вещи.** Один только линтер спецификации считается
  держателем, хотя на сервере, который врёт в каждом поле, он остаётся зелёным. Красить за это
  нельзя: репозиторий, который публикует чужую спецификацию (клиентский SDK, описание чужого
  API), сервером не владеет вовсе. Разбор — `kit/docs/api-e2e.md`.
- **Провал, погашенный `|| true` или `continue-on-error`.** Это `ci-actually-fails` — там же
  теперь опознаются и инструменты про API.
- **Обезвреженного арбитра внутри оболочечного скрипта.** Держателя ищем и в `*.sh`, а вопрос
  «может ли он провалиться» задаём только объявлениям запуска: конвейеру, `Makefile`,
  `justfile`, `package.json`. Внутри скрипта вердикт решают `set -e`, `trap` и явный `exit`, и
  по одной строке о нём судить нельзя — ту же границу проводит `ci-actually-fails`. Поймано на
  себе: наш `smoke.sh` держит образцы в heredoc, и запись покраснела на собственном наборе
  проверок, причём одна находка была в комментарии.
- **Спецификацию с нестандартным именем.** `docs/api/spec.yaml` не опознаётся: имя файла —
  единственный надёжный признак, а `spec.yaml` встречается у чего угодно. Переименуй в
  `openapi.yaml` — так его найдут и чужие инструменты, а не только этот.
- **Сужение другими способами.** Ограничение одним методом (`--include-method GET`), крошечное
  число примеров, выборка путей. Это законные настройки: у проекта бывает причина не трогать
  запись. Красным сделано только то, у чего законного применения нет.
- **Что спецификация вообще описывает этот сервер.** Файл может описывать чужой API; сверять
  их машина не умеет.
