## Приоритет для `audit_project` на 2026-07-13

Этот список — каталог идей, а не backlog «внедрить все 19». Для текущего проекта порядок такой:

### P0 — делать сейчас

1. **Runtime fitness-gates продукта:** queue без production consumer; несовместимые
   `time_limit/visibility_timeout`; тяжёлая task в короткой queue; тяжёлый файл/O(N) fan-out в HTTP.
   Это закрывает уже найденные дефекты, а не гипотетические проблемы харнеса.
2. **Product observability:** HTTP p95/p99/errors, Celery queue depth/oldest age/wait/run,
   PostgreSQL IO/temp/locks, container RSS/OOM/restarts. Агенту позже дать read-only доступ к этим
   данным. Без термометра нельзя ни сайзить, ни проверять производительность.
3. **Workload contract:** короткий реестр `workload → sync/async → queue/consumer → cap → timeout →
   recovery → SLO`. Любая новая фича обязана вписаться в него. Полный roadmap —
   `docs/rebuild/05-load-hardening.md`.
4. **Довести уже существующие гейты до честного состояния:** убрать stale-статусы task/docs,
   проверить branch protection; откалиброванные security/migration/Semgrep gates переводить из
   `allow_failure:true` в blocking по одному, с зафиксированным baseline.

### P1 — после P0

1. **Agent-legible live-stack:** воспроизводимая команда сценария + RO-запросы к логам/метрикам +
   correlation/trace id + короткие debug-рецепты. Per-worktree observability полезна после того,
   как основная телеметрия продукта действительно работает.
2. **Сначала принять решение по headless pipeline:** либо он реально нужен — тогда восстановить
   executable runner и доказать smoke-прогоном; либо пометить dormant и не тратить на него бюджет.
   Checkpointing имеет смысл только после этого.
3. **Typed retry:** transient → backoff; schema/deterministic → один repair; auth/scope → сразу
   человеку. Это дешевле слепых трёх попыток.
4. **Стоимость прогона:** сначала собирать tokens/duration/retry по стадиям; денежный hard budget
   вводить, когда появится реальный расходный порог, а не заранее.

### Не делать сейчас

- векторную/LLM-консолидируемую память — курируемый индекс и repo search пока проще и надёжнее;
- inline LLM-судью на каждый шаг — детерминированные схемы, тесты и Reviewer дают более надёжный сигнал;
- собственный actor-runtime, CodeAct или низкоуровневого агента — используются готовые Claude/Codex;
- произвольные `triggers:` в frontmatter, если runtime их не поддерживает; явный `$skill` и ссылки из
  `AGENTS.md/rules` надёжнее неисполняемого поля;
- OTel GenAI и сложную оптимизацию промптов до появления реально используемого headless pipeline.

# ЧАСТЬ 2 — Детальное раскрытие

## 1. Принудительный структурированный вывод (SGR)

- **Слой:** 🎛 высокий · **Статус у нас:** ◐ **reference-only**. Старый headless runner удалён
  в task-234 как неиспользуемый. Схемы и `scripts/validate_sgr.py` временно сохранены, пока полезные
  требования из SGR не перенесены в обычные rules/checklists.
- **Что это.** Каждый агент возвращает JSON строго по схеме. Этот JSON — **машинный контракт**
  между шагами пайплайна: следующий шаг читает поля предыдущего. Схема = источник истины.
- **Зачем.** Без принуждения структурированный вывод держится «на честном слове модели».
  Агент через раз выдаёт нужную форму → пайплайн молча подхватывает пустоту → багов не видно.
  Принуждение + лог = ты **видишь**, соблюдается ли контракт.
- **Что сохранено на уровне валидатора (не подключено к runtime):**
  1. Объявить схему (✅ есть в `.claude/schemas/`).
  2. Дать схему агенту как инструкцию (✅ есть в `agents/*.md`).
  3. **После** запуска агента — `jsonschema.validate(output, schema)`.
  4. Невалидно → **1 repair**: вернуть агенту список ошибок валидации, попросить починить.
  5. Снова невалидно → **падать громко** + писать кейс в лог (НЕ продолжать с пустыми полями).
  6. Каждый результат валидации (pass/repair/fail) — **в лог/метрику** → появляется
     наблюдаемость соответствия (видно % комплаенса по агентам).
- **Два вида валидации.** (а) **структурная** — JSON против схемы (этот пункт); (б) **смысловая** —
  «правильный ли вывод по сути» (см. пункт 10, Output guardrail). Полноценный гейт = обе.
- **Контракт = схема + инструкция + пример (MetaGPT `ActionNode`).** У них действие несёт не голую
  схему, а связку `expected_type` + `instruction` + `example`, и компилируется в Pydantic-модель.
  Усиление к нашим `schemas/*.json`: рядом со схемой держать инструкцию и пример валидного вывода.
- **Практический вывод:** в интерактивной работе через Codex/Claude этот SGR ничего не проверяет.
  Не чинить его «ради галочки». Если headless pipeline снова понадобится — проектировать новый
  runner отдельной задачей и доказывать живым smoke `agent → output → validation → branch`.
- **Откуда:** твой собственный `rules/general.md` («validate → 1 repair → ошибка») + autogen
  (всё на Pydantic-конфигах с жёсткой валидацией).

## 2. Наблюдаемость прогона (трейсинг)

- **Слой:** 🎛 высокий · **Статус у нас:** ❌ — старый post-hoc wrapper удалён; дерева спанов и
  стандартных атрибутов нет.
- **Что это.** Каждый шаг агента оборачивается в «спан» (отрезок времени с метаданными):
  `invoke_agent`, `execute_tool`, и при ошибке — запись исключения в спан. Спаны связаны
  сквозным `trace_id` → видно дерево «кто кого вызвал и где затык».
- **Зачем.** Сейчас Langfuse у тебя мёртвый именно потому, что нет дисциплины «что трейсить».
  Без спанов прогон — чёрный ящик: агент сказал «готово», а что было внутри — не видно.
- **Как надо.** Стандарт **OpenTelemetry GenAI semantic conventions** (vendor-neutral): спаны
  с атрибутами `gen_ai.operation.name` (`invoke_agent`/`execute_tool`), `gen_ai.agent.name`,
  `gen_ai.tool.name`; на ошибке — `span.record_exception(e)` + `error.type`. Один формат —
  любой бэкенд (Langfuse / Phoenix / Jaeger).
- **Пример атрибутов спана (из autogen `_telemetry/_genai.py`):**
  `{gen_ai.operation.name: "execute_tool", gen_ai.system: "...", gen_ai.tool.name: "pytest"}`.
- **Готовая таксономия спанов (openai-agents `tracing/span_data.py`):**
  `Agent` → `Turn` → `Generation` (вызов LLM) / `Function` (вызов инструмента) / `Handoff`
  (передача между агентами) / `Guardrail`. Вот ровно эти спаны и трейсить.
- **Откуда:** autogen (`_telemetry/_genai.py`, OTel-атрибуты) + openai-agents
  (`tracing/span_data.py`, таксономия спанов). См. также пункт 15 (наблюдаемость ПРОДУКТА для агента).

## 3. Активная память (а не пассивные файлы)

- **Слой:** 🎛 высокий · **Статус у нас:** ⚠️ частично — память пассивная (файлы целиком через
  system-reminder) и плоская (по агентам, без типов).
- **Что это.** Память — не папка, а компонент с методом `update_context()`: она сама
  **запрашивает релевантное** под текущую задачу и **вкидывает только это** в контекст.
  Плюс таксономия: **рабочая** (внутри прогона) / **долгая** (между задачами) / **сущности**
  (факты про модуль/компанию). Контент структурирован: `mime_type` + `metadata`.
- **Зачем.** «Вот тебе вся папка памяти» забивает контекст шумом. «Вот что нужно под эту
  задачу» — точнее и дешевле.
- **Как надо.** Хранилище с query (хоть текстовый поиск, хоть вектор) → отбор top-K
  релевантного → инъекция как отдельный блок. Память сама решает, что показать.
- **Глубже (crewAI `memory/types.py`):**
  - **Композитный скоринг** при recall, не одна похожесть:
    `score = w_семантика·similarity + w_свежесть·decay + w_важность·importance`,
    где `decay = 0.5^(возраст_дней / период_полураспада)`. Свежее и важное всплывает выше.
  - **Консолидация при записи**: при сохранении похожего (similarity > 0.85) LLM решает
    слить/обновить/удалить → память не пухнет дублями. _(у нас есть **ручная** версия: правило
    MEMORY.md «найди файл на эту тему — обнови, не плоди».)_
  - **Лёгкие поля на запись**: `importance` (0-1), `source` (происхождение), `private`,
    `categories`, иерархический `scope` (`/проект/модуль`). Применимо к нашему frontmatter
    без всякого вектор-движка.
  - **Explainable recall**: матч несёт `match_reasons` (почему совпало) и `evidence_gaps`
    (что искал, но не нашёл).
  - Деталь: `embedding` исключён из сериализации (экономия токенов при сохранении).
- **Протокол записи (OpenHands `skills/agent_memory.md`, триггер `/remember`):**
  - логировать ТОЛЬКО переиспользуемое (структура репо, команды build/lint/test, стиль, workflow);
    **НЕ** логировать частности задачи (какую ошибку поймал и как починил);
  - перед сохранением показать **пронумерованный список** того, что собираешься записать →
    сохранить **только одобренные** пункты → интегрировать в существующее, не плодить.
  - _(у нас правило похожее, но мягче — стоит формализовать «список → апрув подмножества».)_
- **Честная граница.** Полный вектор-движок для нашей маленькой курируемой памяти — 🔧 перебор.
  Берём ЛЁГКИЕ идеи (🎛): `importance`/`source`/`scope` в frontmatter + дисциплина консолидации.
- **Уровни памяти (Letta/MemGPT `schemas/memory.py`) — каноничный паттерн:**
  - **core memory** — в контексте всегда, маленькая, с char-лимитом, агент САМ её редактирует
    (вынужден приоритизировать); **archival/recall** — внешние, подгружаются поиском по запросу.
  - `ContextWindowOverview` — точная разбивка бюджета контекста по секциям (system/core/summary/
    messages/functions) — наблюдаемость самого контекста.
  - блоки **версионируются** (git-backed history).
  - _(у нас это УЖЕ есть в зачатке: `MEMORY.md` = core-индекс (всегда), отдельные файлы =
    archival (по релевантности). Letta подтверждает паттерн; усиление — бюджет/лимит на core.)_
- **Откуда:** autogen (`memory/_base_memory.py`, `update_context`/`query`/`MemoryContent`) +
  crewAI (`memory/types.py`, `memory_scope.py`: composite score, consolidation, scopes) +
  OpenHands (`skills/agent_memory.md`: протокол записи с апрувом) +
  Letta (`schemas/memory.py`: уровни core/archival/recall, self-editing, context-budget).

## 4. Хуки-«таможня» (вмешательство на лету)

- **Слой:** 🎛 высокий · **Статус у нас:** ⚠️ частично — есть PreToolUse deny и PostToolUse
  auto-format; Stop пока только уведомляет и не является quality stop-gate.
- **Что это.** Перехватчик, срабатывающий на каждое действие агента, который может его
  **изменить, залогировать или отклонить** ДО выполнения (не после).
- **Зачем.** Блокировка по факту коммита ловит поздно. Перехват до действия — дешевле и
  позволяет править («подставь правильный путь», «не трогай файл вне Scope») на лету.
- **Как надо.** У Claude Code это `PreToolUse`-хуки: получают вызов инструмента до исполнения,
  возвращают allow/deny/изменение. Использовать не только для запретов, но и для корректировок.
- **Дизайн из crewAI (`hooks/types.py`) — 4 точки перехвата:**
  - `before_tool_call` → правит вход инструмента *на лету* ИЛИ `False` = заблокировать.
  - `after_tool_call` → переписывает результат инструмента.
  - `before_llm_call` / `after_llm_call` → то же для сообщений/ответа модели.
  - Контракт: «before» возвращает `bool|None` (False = стоп), «after» возвращает `str|None`
    (str = изменённый результат). Чисто, предсказуемо.
- **Откуда:** autogen (`_intervention.py`, `InterventionHandler`/`DropMessage`) +
  crewAI (`hooks/types.py`: before/after × LLM/tool, modify-or-block).

## 5. Алгоритмы ужатия контекста при передаче между агентами

- **Слой:** 🎛 высокий · **Статус у нас:** ❌ нет алгоритмов (есть скилл `context-engineering`,
  но это прозаические советы).
- **Что это.** Конкретные стратегии, как обрезать историю/контекст, не теряя главного:
  - **head+tail+«пропущено N»**: оставить первые N (инструкции) и последние M (свежее),
    середину заменить плейсхолдером `"Skipped 42 messages"`.
  - **token-limited middle-drop**: пока не влезаем в бюджет — выкидывать из **середины**.
  - дисциплина краёв: не оставлять висящий вызов функции или его результат на стыке.
- **Зачем.** Когда Archivist ужимает историю, Planner отдаёт контекст Builder'у — нужна не
  «отрежь сколько-то», а стратегия, что именно беречь.
- **Откуда:** autogen (`model_context/`: `HeadAndTailChatCompletionContext`,
  `TokenLimitedChatCompletionContext`, `BufferedChatCompletionContext`).

## 6. Предел итераций агента ✅

- **Слой:** 🎛 высокий · **Статус у нас:** ✅ есть — правило «макс 3 итерации → СТОП, вернуть человеку».
- **Что это.** Жёсткий лимит на число попыток, чтобы агент не крутился вечно.
- **Откуда:** autogen (`max_tool_iterations`). У нас уже реализовано как правило пайплайна.

## 10. Output guardrail (LLM-судья на вывод шага)

- **Слой:** 🎛 высокий · **Статус у нас:** ⚠️ частично — есть тяжёлые Reviewer/JiTTest в конце
  пайплайна, но нет лёгкого inline-гейта на каждый шаг.
- **Что это.** К шагу привязывается критерий **словами** («вывод: 10 буллетов, без воды»).
  Отдельный агент-судья проверяет результат и возвращает **структуру** `{valid: bool, feedback: str}`.
  Невалидно → фидбек возвращается, шаг переделывается (ретрай).
- **Зачем.** Схемная валидация (пункт 1) ловит только *форму*. Guardrail ловит *смысл*:
  «по делу ли», «нет ли галлюцинации», «соблюдён ли бизнес-критерий».
- **Дисциплина.** Судье запрещено чинить — только указывать на проблемы
  («identify issues — do not propose corrections»). Критика отделена от исправления.
- **Как надо.** `valid/feedback` — структурированный вывод судьи (тот же пункт 1!). Лёгкий
  guardrail на шаг ≠ тяжёлый Reviewer в конце: дешевле и ловит раньше. Спец-вариант —
  guardrail на галлюцинации (crewAI `tasks/hallucination_guardrail.py`).
- **Вход И выход + tripwire (openai-agents `guardrail.py`):** guardrail бывает на **вход**
  (проверить задачу ДО прогона — не жечь токены на заведомо кривой запрос) и на **выход**.
  Результат несёт `tripwire_triggered: bool` — если сработал, прогон **немедленно останавливается**
  (исключение `…TripwireTriggered`). Декораторы `@input_guardrail`/`@output_guardrail`.
- **Откуда:** crewAI (`tasks/llm_guardrail.py`, `LLMGuardrailResult{valid, feedback}`) +
  openai-agents (`guardrail.py`: input/output guardrails, tripwire-halt).

## 11. Учёт стоимости + бюджет задачи

- **Слой:** 🎛 высокий · **Статус у нас:** ❌ — отдельного runner, учёта стоимости и потолка нет.
- **Что это.** Считать **деньги** за прогон: `$ = токены × цена_модели` (таблица цен на модель).
  Вести бюджет на задачу/агента/период и **резать**, когда превышен.
- **Зачем.** Сейчас задача может тихо прожечь любой объём токенов. Потолок = предсказуемость
  расходов + ранний стоп зацикленного агента по деньгам, а не только по итерациям.
- **Как надо.** (1) таблица цен модели; (2) после каждого шага: `cost += in·price_in + out·price_out`;
  (3) лимит на задачу → превышен → стоп + лог. Связано с наблюдаемостью (пункт 2): стоимость — метрика.
- **Откуда:** litellm (`cost_calculator.py`, `budget_manager.py`,
  `model_prices_and_context_window_backup.json`).

## 12. Типизированный retry (по классу ошибки)

- **Слой:** 🎛 высокий · **Статус у нас:** ⚠️ частично — «макс 3 итерации» слепо на любую ошибку.
- **Что это.** Число и стратегия повторов зависят от **типа** сбоя:
  - временное (timeout, rate-limit) → повторить (возможно с backoff);
  - детерминированное (bad-request, невалидная схема, синтаксис) → повтор не поможет → **1 repair или стоп**;
  - блокирующее (auth/доступ) → **не повторять**, сразу человеку.
- **Зачем.** Слепой ретрай на детерминированную ошибку жжёт попытки впустую; временную, наоборот,
  стоит повторить больше раз. У тебя уже есть таксономия ошибок в скилле `metrics-analysis`
  (IMPORT/ASSERT/RUNTIME/DB/TYPE) — её надо **подключить к стратегии ретраев**, а не только к аналитике.
- **Откуда:** litellm (`router_utils/get_retry_from_policy.py`: `RetryPolicy` с полями
  `TimeoutErrorRetries`/`RateLimitErrorRetries`/`BadRequestErrorRetries`/…).
- **ℹ️ К сведению (низкоуровневое, если строишь агента/прокси):** reason-aware fallback
  (`context_window_fallbacks` → переключение на модель с бОльшим окном; `content_policy_fallbacks`),
  circuit-breaker (cooldown упавшего провайдера после `allowed_fails`), семантический кэш
  (кэш по смыслу промпта). Для нашей dev-среды на одном opus-4-8[1m] — не применимо.

## 13. Явные триггеры + версия скилла

- **Слой:** 🎛 высокий · **Статус у нас:** ⚠️ частично — явные `$skill`-вызовы доступны, но
  автоматическое срабатывание по `description` не измеряется.
- **Что это.** Использовать только реальный контракт конкретного runtime: явный `$skill`/команду,
  конкретный `description` и ссылки из `AGENTS.md`/rules. Версию хранить через git или поддерживаемое
  поле runtime.
- **Зачем.** Семантический триггер гибкий, но недетерминированный. Неисполняемое поле
  `triggers:` создаёт ложную гарантию и потому хуже явного указателя.
- **Как надо.** Критические процедуры подключать явной ссылкой или вызовом, а факт применения
  логировать там, где runtime это поддерживает.
- **Откуда:** OpenHands (`skills/*.md`: `name/type/version/agent/triggers`; keyword + slash-команды).

## 15. Agent-legible продукт (наблюдаемость продукта ДЛЯ агента) ⭐

- **Слой:** 🎛 высокий · **Статус у нас:** ❌ нет.
- **Что это.** Не «трейсить агента» (пункт 2), а сделать **сам продукт читаемым для агента**:
  приложение поднимается на каждый git-worktree, его логи/метрики/трейсы доступны агенту
  через локальный эфемерный observability-стек (запросы LogQL/PromQL/TraceQL), а UI — через
  Chrome DevTools. Тогда промпт «убедись, что старт сервиса < 800мс» или «ни один из 4 сценариев
  не дольше 2с» становится **исполнимым** — агент сам воспроизводит баг, чинит, проверяет, повторяет.
- **Зачем.** Это то, что позволило OpenAI собрать продукт в 1М строк силами 3-7 инженеров:
  узкое место — человеческое QA; убираешь его, дав агенту самому видеть поведение продукта.
- **Как надо (для нас).** У тебя уже есть Live-stack E2E (агент сам гоняет реальный стек). Развить:
  per-worktree подъём + RO-доступ агента к логам/метрикам + «дёрни и проверь по трейсам».
- **Откуда:** OpenAI «Engineering the harness: Codex» (2026).

## 16. AGENTS.md = оглавление + docs/ как система записи

- **Слой:** 🎛 высокий · **Статус у нас:** ✅ для Codex — `AGENTS.md` занимает 72 строки и ведёт
  в профильные docs; ⚠️ для Claude — `CLAUDE.md` длиннее целевого бюджета и требует housekeeping.
- **Что это.** Не пихать всё в один большой файл инструкций (он вытесняет задачу из контекста,
  «важно всё → важно ничто», устаревает, не проверяется). Вместо этого: **короткий вход** (~100 строк)
  = карта с указателями → структурный `docs/` (design-docs, exec-plans active/completed,
  product-specs, references, QUALITY_SCORE.md, ARCHITECTURE.md) как **система записи**.
  **Progressive disclosure**: агент стартует с малого и знает, куда смотреть дальше.
- **Механически:** линтеры + CI проверяют свежесть/перекрёстные ссылки; периодический
  **doc-gardening агент** находит устаревшую доку и открывает PR.
- **Артефакт QUALITY_SCORE.md:** оценка каждого домена/слоя + отслеживание пробелов во времени.
- **Откуда:** OpenAI Codex blog (структура `docs/`, ToC-подход, doc-gardening).

## 17. Линтер с инструкцией по починке в тексте ошибки

- **Слой:** 🎛 высокий · **Статус у нас:** ✅ — `arch-lint.sh` для ключевых правил уже сообщает
  конкретный способ исправления и ссылку на норму. Новые fitness-gates должны продолжать этот контракт.
- **Что это.** Кастомный линтер инвариантов формулирует сообщение об ошибке так, чтобы **встроить
  инструкцию по устранению прямо в контекст агента** → агент сам чинит, не гадая.
- **Зачем.** Линтер = feedforward+feedback для агента: «инвариант нарушен, вот КАК исправить».
  После внедрения применяется везде одновременно (множитель).
- **Откуда:** OpenAI Codex blog («внедряем инструкции по устранению в сообщения об ошибках линтера»).

## 18. Eval-driven оптимизация промптов/скиллов

- **Слой:** 🎛 высокий · **Статус у нас:** ⚠️ — Evolver мутирует эвристично (`metrics.json`),
  без метрики+eval-набора+optimizer'а.
- **Что это.** Промпт/описание скилла — **обучаемый параметр против метрики**: задаёшь метрику
  и небольшой eval-набор → optimizer (GEPA/MIPRO/BootstrapFewShot) **предлагает варианты → скорит →
  оставляет лучший**. То же для описаний скиллов (бенчмарк срабатывания → авто-улучшение описания).
- **Зачем.** Убирает гадание «лучше ли стал промпт» — есть число, а срабатывание скиллов становится
  измеримым.
- **Откуда:** DSPy (`teleprompt/gepa`, `mipro_optimizer_v2`, `bootstrap`) и deer-flow
  (`skill-creator/scripts/run_eval.py`, `improve_description.py`).

## 19. Возобновляемые прогоны (checkpointing)

- **Слой:** 🎛/🔧 · **Статус у нас:** N/A — headless runner отсутствует.
- **Что это.** Прогон сохраняет состояние по шагам (checkpoint) и может **продолжиться с места**
  после сбоя/паузы/правки, не начиная заново.
- **Зачем.** Длинные прогоны (часы) не теряются из-за одного сбоя; дешевле MTTR.
- **Откуда:** deer-flow (`runtime/checkpointer`, `persistence/run`), Letta (версионируемые блоки);
  тема LangGraph (checkpoints/time-travel) — если понадобится глубже.
