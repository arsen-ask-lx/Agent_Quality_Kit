# Эксплуатационные гейты из живого AI-проекта: что переносить, а что не притворять универсальным

> Проверено по коду `audit_project` 15.09.2026, ссылки на первоисточники сверены 16.09.2026. Это актуальная карта практики, а не ручной
> снимок production-метрик. Живые значения остаются в Prometheus, логах и отчётах прогонов.
>
> Главная граница: здесь описаны **намерения и устройство арбитров**. Реализация конкретного
> Django/Celery/Compose-проекта остаётся в его репозитории и объявляется в `.aqk.yml` командой,
> а не копируется в AQK.

## Один вывод

Зелёная фича ещё не означает зелёную систему. Query budget одной ручки, memory budget одной
задачи и тест одного worker не отвечают на вопрос, выдержит ли одновременно работающий флот
общую RAM, PostgreSQL, Redis, диск и очередь.

Поэтому бюджетов всегда два:

1. **локальный** — SQL, время, память и корректность одного endpoint/task;
2. **системный** — p95, error rate, суммарный working set, очереди и OOM под смешанной нагрузкой.

## Карта по факту

| Область | Что действительно держит машина | Честная граница |
|---|---|---|
| N+1 | 21 тестовый файл и 63 вызова `assertNumQueries` / `django_assert_max_num_queries`; полный pytest блокирует рост известных бюджетов | нет требования, что **каждая новая** list/paginated-ручка получила budget-тест |
| DirectPG N+1 | отдельный тест проверяет не только число запросов, но и отсутствие линейного роста на увеличенном наборе | это проектный арбитр, обычный Django-счётчик его не заменяет |
| OOM после факта | `ContainerOOM` на росте `container_oom_events_total`; выражение имеет firing и quiet сценарии `promtool` | cAdvisor в основном описывает работающие контейнеры; история exited/restart требует отдельного источника |
| Лимиты observability | тест разбирает Compose и держит сумму лимитов tier под явным капом | это кап одного tier, не бюджет всего production-флота и не резерв RAM хоста |
| Celery topology | объявленные/используемые очереди сравниваются с `worker -Q` в production Compose | имена и структура конфигурации проектные |
| Celery redelivery | `visibility_timeout` сравнивается с максимальным hard time limit и запасом | длинный timeout ухудшает скорость возврата работы после принудительной смерти worker |
| Публичные метрики | publisher обязан попасть в реестр; быстрый pre-commit ловит забытое имя, pytest проверяет глубокую проводку | наличие имени не доказывает, что production реально его собирает |
| Prometheus rules | синтаксис и выбранная семантика правил проверяются `promtool`; после deploy сверяется набор реально загруженных правил | не каждое правило уже имеет отдельные firing/quiet samples |
| Скрипты-гейты | `check-gate-wiring.py` требует автоматический запуск либо честную запись в реестре ручных инструментов | «запускается» не означает «полезен»; это другой вопрос |
| Ошибки и trace | GlitchTip, Sentry SDK, Loki/Alloy и `request_id` связывают исключение с окружением запроса | доступность самой цепочки также нуждается в heartbeat/alert |
| Backup | расписание, ротация, метрика успеха, `BackupStale` и тесты скрипта | копия на том же сервере не переживёт потерю сервера; restore надо репетировать отдельно |

## Что ещё только видно, но не закрыто

Наличие графика или Telegram-alert не равно предотвращению.

### Память

- нет ранней полосы «контейнер долго держится выше доли своего лимита»;
- нет отношения `sum(container working_set) / host RAM` для всего флота;
- нет host-level RAM/swap/PSI прибора уровня node exporter;
- нет долговечной истории OOM/restart для уже остановившихся контейнеров;
- нет memory budgets для всех тяжёлых pytest-сценариев;
- сумма отдельных потолков не является резервированием общей памяти.

Последний пункт особенно важен. Docker ограничивает отдельный сервис, но несколько сервисов
могут одновременно приблизиться к своим пределам и исчерпать хост. Поэтому static Compose gate
и runtime fleet gate решают разные задачи; один нельзя выдавать за другой.

### PostgreSQL и Redis

Экспортёры есть, но нужны отдельные решения по сигналам:

- насыщение соединений и ожидание PgBouncer;
- длинные транзакции, deadlocks, temp bytes и блокировки;
- память Redis broker при `noeviction`;
- rejected writes, а не только evictions;
- возраст старейшей работы и ожидаемое время разбора очереди, а не одна глубина.

### Нагрузка

- Python load harness измеряет p50/p95/p99 и RPS, но плохие числа сами не дают красный код;
- k6 thresholds существуют лишь у отдельных ручных сценариев;
- нет обязательного смешанного прогона HTTP + Celery + отчёты + документы + интеграции;
- нет nightly/pre-release запуска;
- нет регулярного soak для утечек, high-watermark процессов и накопления соединений.

## Как строится честный OOM-контур

Одного правила `any OOM` мало. Нужны пять независимых слоёв.

### 1. Статические лимиты сервисов

Production Compose задаёт `deploy.resources.limits.memory` или эквивалент. Проверка разбирает
эффективную конфигурацию, а не ищет слово `memory` grep-ом. Для каждого обязательного сервиса
должно быть ясно, почему лимит такой и каким замером он получен.

### 2. Конфигурационный бюджет

Сумма лимитов выбранного tier не растёт молча. Это храповик конфигурации, а не обещание, что RAM
зарезервирована. Поднять кап можно только вместе с измерением хоста и записанной причиной.

### 3. Runtime budget флота

Под смешанной нагрузкой считается:

```text
max_over_time((sum(container_memory_working_set_bytes))[15m:1m]) / host_memory_bytes
```

Точный PromQL зависит от labels и источника host memory. Порог нельзя копировать вслепую; для
малого сервера разумная стартовая красная полоса должна оставлять запас ядру, Docker, page cache
и пикам PostgreSQL. В исследованном проекте рабочей гипотезой остаётся 70%, но она ещё не стала
доказанным гейтом.

### 4. Раннее предупреждение контейнера

Устойчивое превышение доли лимита предупреждает до OOM. Рабочая гипотеза проекта — около 85%,
но её надо откалибровать по пикам и шуму. Мгновенный spike и десять минут давления — разные
события.

### 5. OOM и restart после факта

Рост `container_oom_events_total` — critical. Но исчезновение ряда остановленного контейнера не
должно превратить аварию в тишину: Docker events/inspect или другой collector хранит exit reason,
restart count и timestamp независимо от текущей жизни контейнера.

### Доказательство правила

Для alert нужны минимум два `promtool`-сценария:

- counter вырос внутри окна → alert firing с ожидаемыми labels/annotations;
- counter не растёт → alert отсутствует.

Синтаксически корректное выражение `vector(0)` обязано сделать первый сценарий красным. Если вся
батарея остаётся зелёной, семантика OOM не проверяется.

## Как строится N+1-гейт

Один статический поиск `select_related` ничего не доказывает. Арбитр должен наблюдать полный
операционный путь.

1. Создать больше одного связанного объекта; для list endpoint обычно нужны десятки строк.
2. Выполнить настоящий HTTP-запрос или функцию задачи.
3. Зафиксировать постоянный максимум SQL, а не `текущее число + 1`.
4. Увеличить объём fixture и проверить, что число запросов не растёт линейно.
5. Запускать тест в общей блокирующей батарее.

Django официально предоставляет `assertNumQueries`. Для pytest допустима обёртка с верхним
пределом, если она печатает выполненные запросы при превышении. Direct SQL, Trino и внешние базы
нуждаются в своём счётчике — ORM-инструмент не видит их по построению.

Честная граница: наличие двадцати одного budget-теста не доказывает покрытие двадцать второй ручки.
Отдельный coverage-gate возможен только тогда, когда проект умеет машинно определить множество
ручек, для которых budget обязателен. Проверять слово в имени теста недостаточно.

## Два инварианта Celery

### Очередь имеет потребителя

Сопоставляются три факта:

- очереди, объявленные в настройках;
- очереди, используемые routes, task decorators и `apply_async`;
- очереди, которые реально слушают production workers.

Новая очередь без consumer красит CI. Документ или диаграмма не являются источником истины.

### Доставка не опережает hard timeout

Redis visibility timeout определяет, когда неacknowledged message возвращается в очередь. Если
задача законно выполняется дольше, второй worker может получить её повторно. Проектный гейт
сравнивает отношения настроек и fail-closed обрабатывает неразрешимые значения.

Это не универсальная формула для всех Celery-систем: ETA/retry и принудительное завершение
создают обратную цену слишком большого timeout. Инвариант должен учитывать модель задач проекта.

## Метрика и алерт — это цепочка, а не файл

Полный путь выглядит так:

```text
код публикует имя
  → exporter его принимает
  → Prometheus scrape видит ряд
  → правило вычисляется правильно
  → Alertmanager маршрутизирует
  → человек получает сообщение
  → runbook говорит, что делать
```

Для каждого шва нужен свой арбитр. Unit-test publisher не доказывает scrape. `promtool check`
не доказывает смысл выражения. Тест выражения не доказывает, что production загрузил новый файл.
После deploy полезна read-only сверка repo rule names с Prometheus API.

## Нагрузочный гейт и soak

Короткий mixed scenario должен иметь код возврата и одновременно держать:

- error rate;
- p95 ключевых пользовательских путей;
- throughput или время разбора очередей;
- суммарный working set флота;
- отсутствие OOM/restart;
- при необходимости соединения PostgreSQL и rejected writes Redis.

Короткий прогон не ловит медленную утечку. Soak запускается отдельно и реже, с теми же
инвариантами, но с проверкой тренда памяти, соединений и очередей во времени. Смешивать soak с
каждым pre-push нельзя: дорогой гейт начнут обходить.

## Где здесь агент

Агент не должен решать, случилась ли аномалия. Сначала детерминированный detector:

```text
Prometheus rule или baseline script
  → фильтрация и группировка события
  → краткоживущий read-only агент
  → гипотеза + evidence + confidence + связанный deploy
  → issue / intent / merge request
  → решение человека
```

По расписанию работает baseline script. Модель вызывается только по нарушению полосы. На первом
этапе ей достаточно read-only доступа к Prometheus, Loki, error tracker и истории deploy; права
на production DB, Docker socket, merge и произвольный runbook не нужны.

## Как подключать это через AQK без дублей

AQK-манифест объявляет **существующую команду проекта**:

```yaml
gates:
  project-verify: "bash scripts/verify.sh"
  prometheus-rules: "docker run --rm ... promtool test rules alerts_test.yml"
groups:
  code: [project-verify]
  observability: [prometheus-rules]
```

Внутренние шаги `project-verify` не перечисляются второй раз в манифесте. При падении агрегатор
обязан назвать конкретный шаг. Отдельным gate становится только команда, которую агрегатор
честно не запускает.

Один gate AQK получает не больше пяти минут. Если полный verifier проекта дольше, в манифесте
нужен его быстрый блокирующий режим, а `--full` — отдельный прямой или CI-прогон. Иначе AQK будет
честно возвращать «не смог проверить: timeout», но интеграция не станет рабочим локальным gate.

Не надо:

- копировать project-specific Python checks в `kit/gates`;
- объявлять grep по словам `memory` или `assertNumQueries` доказательством;
- указывать похожий каталог как `samples`, если структура AQK red/green там отсутствует;
- повышать уровень AQK заглушками;
- запускать `aqk init --force` поверх зрелого корпуса правил без review.

Новая запись каталога AQK появляется после трёх доказательств: устойчиво опознаваемая конструкция,
red/green samples и переносимый рецепт с понятной границей ложных срабатываний. До этого это
методика или собственный gate проекта — и это честное состояние.

## Порядок для нового проекта

1. До кода записать измеримые AC: SQL, p95, error rate, memory, очередь, идемпотентность.
2. Быструю детерминированную статику поставить в pre-commit.
3. Query и task budgets поставить в обычный CI.
4. Compose limits и alert rules проверять нативными валидаторами.
5. Mixed load запускать nightly и перед релизом; soak — отдельно, например еженедельно.
6. Любой OOM сделать красным исходом и сохранить причину после смерти контейнера.
7. Только после стабилизации сигналов подключать read-only агента к нескольким critical alerts.

## Финальный принцип

> Сначала детерминированный сигнал и ограничение. Потом агент. Никогда наоборот.

Повторившаяся ошибка должна оставлять после себя не ещё один абзац, а арбитр с кодом возврата.
Если переносимого арбитра пока нет, граница называется вслух — текст не получает фальшивое имя
«гейт».
