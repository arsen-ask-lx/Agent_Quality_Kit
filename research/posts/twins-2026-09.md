# Кто проверяет ваши проверки

> **Черновик статьи для публикации наружу (Хабр, затем английская версия для HN).**
> Готов к вычитке владельцем; публикует человек, не комплект.
> Все числа сверены с первоисточником 2026-09-14: разборы в `research/competitors/`,
> замер на чужих репозиториях — в `incidents/README.md` (запись 2026-09-11).

---

В репозитории стоят линтер, тесты, хук перед коммитом и конвейер. Все зелёные. Вопрос, который
почти никто себе не задаёт: **а они вообще способны покраснеть?**

Проверка бывает выключена (`|| true`, `continue-on-error: true`, `--exit-zero`), настроена на
пустой каталог, запускается не на том шаге, падает молча внутри обёртки. Во всех этих случаях
она выглядит **точно так же, как работающая**: зелёная галочка. Отличить одну от другой, глядя на
вывод, нельзя по построению — это и есть главная беда всей оснастки вокруг агентов.

Ниже — воспроизводимый способ отличить, и что он показал на живых инструментах, включая наш.

## Метод: близнецы

Берём два проекта, одинаковых во всём, кроме **способности проверки провалиться**:

| | настоящий | поддельный |
|---|---|---|
| `package.json` | `"test": "node --test"` | `"test": "node --test \|\| true"` |
| тест | с `assert` | без единого утверждения |
| шаг конвейера | обычный | `continue-on-error: true` |
| хук перед коммитом | `npm test` | `npm test \|\| true` |

Инструмент, который утверждает, что оценивает качество обвязки, обязан дать на этих двух проектах
**разные** ответы. Если ответы одинаковые — он меряет наличие файлов, а не наличие защиты.

Метод дешёвый: пара близнецов делается за десять минут, и повторить его может кто угодно.

## Что показали близнецы

Мы прогнали на этой паре **AgentLint** (`0xmariowu/AgentLint`, коммит `7a22cf6`, 56 звёзд, замер
2026-09-11) — 51 детерминированная проверка, оценка 0–100, плагин Claude Code, GitHub Action.
Вещь сделанная всерьёз: 2252 строки сканера, у каждой проверки ссылка на источник.

**Результат: 71 и 71. Все 51 проверка — одинаковые оценки.**

Наша проверка `ci-actually-fails` на той же паре: **0 и 1**.

Оговорка, без которой это было бы нечестно: инструменты про разное. Их 51 проверка — про **форму**
обвязки (есть ли свод, есть ли команды, закреплены ли действия по SHA), и в этом они находят
настоящее: у нас они нашли `pull_request_target` в рабочем процессе и незакреплённые действия.
Близнецы просто показывают, что **вопрос «работает ли проверка» их набором не задаётся**.

## Проверка, которая ошиблась в обе стороны

У них есть проверка, ближе всех подходящая к этому вопросу, — H7 «ворота в конвейере
блокирующие». Устроена так (`scanner.sh:1951-1979`):

```sh
if printf '%s' "$wf_name" | grep -qiE '(required|gate|test-required|size|check)'; then
  ...
  if ! printf '%s' "$wf_content" | grep -qE 'exit[[:space:]]+1'; then
    h7_warn_only=$((h7_warn_only + 1))
```

То есть «ворота» — это файл, в **имени** которого есть `gate`, `check`, `required` или `size`, а
«блокирующие» — те, в **тексте** которых встречается `exit 1`.

Опыт: те же близнецы, `ci.yml` переименован в `check.yml`, в поддельный дописан комментарий
`# on failure the step does exit 1`.

| | что на деле | вердикт H7 |
|---|---|---|
| настоящий | `npm test` роняет шаг | «warn-only (always exit 0) — they never block merge» |
| поддельный | `continue-on-error: true` | «All 1 gate workflow(s) are blocking» |

Ровно наоборот в обе стороны. И заметьте: **починить это переименованием файла** — значит
«улучшить оценку», ничего не изменив в защите.

## «Точность 99 %», которая мерит согласие с собой

В том же проекте есть то, чего нет почти ни у кого: замер точности на **4533 размеченных
репозиториях**, точность по проверкам 0,99+. Идея правильная и редкая.

Но разметку делает `auto-label.js` по файлу `check-spec.md`, у которого в шапке написано
«Extracted from `src/scanner.sh`». То есть эталон извлечён из того самого сканера, который по
нему и оценивают. Число меряет, что сканер согласен со своим пересказом, — а не что он находит
беду. Одна из проверок, например, «проходит», если в своде встречается слово `checklist`.

Это не обман: это ловушка, в которую попадает любой, кто размечает корпус тем же кодом, который
проверяет. Разметка должна идти **от свойства проекта** («здесь проверка способна провалиться»),
а не от пересказа правила.

## Замер на чужих репозиториях: 9 из 99

Ещё один способ проверить, не выдумана ли проблема, — посмотреть на чужой код.

Поиск по GitHub: файлы `AGENTS.md` (свод правил для агента), в которых упомянута команда
`npm run …`. Первая сотня файлов, 99 репозиториев. Считаем командой несуществующей только если её
нет **ни в одном** `package.json` репозитория (чтобы рабочие пространства и `cd frontend && npm
run …` не давали ложных).

Сырой счёт — 12 из 99. Три отпадают по собственным правилам замера (свод сам говорит, что команды
сняты; `npm run cms:<имя>` — шаблон, а не команда). **Остаётся 9 из 99.**

Два случая, где видно, как это происходит:

- `notefig/notefig` — скрипт `lint:cli` добавлен вместе со строкой в `AGENTS.md` (31 марта) и
  **в тот же день** удалён коммитом «fix(ci): resolve GitHub Actions failures». Свод по сей день
  велит `npm run lint:cli`.
- `JonnyKreng/pebble-navi` — скрипт `debug` добавлен 5 июня вместе со строкой
  `npm run debug  # build + install + logs`, удалён через два дня. Строка осталась. Здесь же
  ловушка для проверяющего: `debug` есть в **зависимостях**, и поиск любого `"debug":` в файле дал
  бы ложное «скрипт есть».

Каждый десятый свод велит агенту команду, которой в проекте больше нет. Агент её выполнит,
получит ошибку и пойдёт «чинить» то, что не ломалось.

## Та же болезнь у нас

Было бы нечестно закончить на соседях.

13 сентября внешний разбор нашёл в нашем комплекте ровно этот класс отказа. У нас есть флаг
`--since`, который сужает вывод проверок до изменённых файлов — чтобы годы чужого долга не валили
сегодняшний коммит. Сужение шло **по путям** в выводе. И под него попадала не только старая
находка, но и проверка, которая **вообще не смогла отработать**: нет инструмента, неожиданный код
возврата, убита сигналом. Такая проверка называет в жалобе какой-нибудь путь; если путь не в
дифе — строк не остаётся, и прогон печатает зелёную галочку.

**Проверка сломалась → инструмент сказал «чисто».** Ровно то, против чего он написан.

Девяносто собственных проверок этого не видели: класс отказа был известен и проверялся **в самих
проверках**, но дорогу через флаг сужения никто не прошёл. Починено, красный тест написан до кода,
в журнал шишек записан вывод, который дороже правки: класс отказа проверяется на всех дорогах, а
не там, где его однажды встретили.

## Что из этого следует

Единственный честный способ узнать, работает ли проверка, — **подсадить в проект брак и
посмотреть, заметит ли она**. Всё остальное меряет наличие файлов.

Отсюда вырос [AQK](https://github.com/arsen-ask-lx/Agent_Quality_Kit) — CLI без единой
зависимости (`npx agent-quality-kit doctor`), который:

- берёт самый горячий по истории починок файл, подсаживает в **копию** известный класс брака и
  гоняет по нему **ваши объявленные** проверки — «поймано» засчитывается, только если проверка
  назвала подсаженный файл и промолчала на исправном образце;
- различает три исхода запуска, а не два: **чисто · находка · не смогли проверить**;
- говорит вслух, чего его собственная ступень **не** доказывает.

И, раз уж статья про честность замеров: у комплекта **один посторонний пользователь за всё
время**, и тот ушёл, оставив разбор. Тысяча скачиваний в неделю в npm — это зеркала реестра и
сканеры, а не люди: версии качаются равномерно, включая ту, что прожила двадцать пять минут.

Поэтому просьба прямая. Прогоните на своём репозитории и скажите, **что он у вас не смог
проверить** — это ценнее похвалы:

```bash
npx agent-quality-kit doctor --run
npx agent-quality-kit feedback   # соберёт письмо; отправляете вы, ничего не уходит само
```

## Что мы взяли у соседей

Раз уж разбирали чужое — честно назвать, что забрали:

- **пометки находок прямо в pull request** (`::error file=…,line=…`) — идея их, реализация наша,
  экранирование сверено с официальным `@actions/core`;
- **идею постоянного корпуса настоящих репозиториев** — но с разметкой по свойству проекта, а не
  по пересказу правила;
- **поворот в `learn`**: искать не только сказанное вслух и не записанное, но и правило, которое
  **уже записано**, а человек всё равно продолжает поправлять агента. Такому правилу текста мало,
  нужен сторож.

Инструмент, который мы разбирали, — живой, с ясным кодом и с замером, которого нет у большинства.
Всё сказанное выше относится к одному коммиту на одну дату и проверяется за десять минут парой
близнецов. Сделайте её для своего инструмента. Ответ бывает неожиданным.
