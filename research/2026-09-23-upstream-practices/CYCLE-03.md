## Кандидаты «взять»
- `--preview`: результат отбора файлов с причиной исключения каждого, без затрат. У нас: report показывает .aqkignore — сверить полноту.
- `ocr rules check <path>`: какой слой и какой шаблон победил. У нас: выбор рецепта в report — сверить, называем ли причину.
- страж покрытия в группировке: файл, не приписанный моделью, всё равно ревьюится отдельно. Наш принцип «ничего не теряется молча».

## cli-reference
- ПОДТВЕРЖДЕНИЕ нашего решения: `session compare` — четыре корзины, «not reviewed» НЕ считается resolved. Мы пришли к тому же сегодня (пропавшая проверка ≠ починка). Взять слово и форму: четыре корзины, а не «лучше/хуже».
- статус прогона 4 значения + skipped отдельно от «нет находок». У нас: ok/fail/cannot на гейт; на прогон — partial. Сверить: есть ли у нас «прогон пропущен, нечего проверять» отдельно от «чисто».
- ДЫРА-КАНДИДАТ (их): exit 0 при completed_with_warnings/errors — CI зелёный при непросмотренных файлах. Проверить по коду и по их action.yml/примерам CI: смотрит ли кто-нибудь status.
- `--output` лениво: упавший прогон не затирает прежний файл. Проверить у нас: doctor --run пишет last-run.md/report.html даже при падении?
- `--max-tools` 1–49 молча → 50: заданное значение подменено без слова (документировано). Класс «порог подменён молча».

## faq / installation
- ГЛАВНОЕ ПРОТИВОРЕЧИЕ С AQK: exit 0, если хоть что-то прошло; упавшие подагенты и пропущенные по токенам группы — только warnings. Их компенсация — manifest.terminal_state + coverage в JSON. Прочитать manifest в коде: какие состояния покрытия, кто их читает (action.yml, CI-примеры, плагины)?
- «Файл без замечаний — смотрели ли его?» решается руками в viewer, либо coverage. У нас этот вопрос закрыт `report --since` (назван / обойдён / не тронут) — сравнить с их coverage.
- автообновление по умолчанию — у нас сознательно нет. Не брать.
- противоречие в installation.md: «upgrades automatically» vs «prints an upgrade hint».

## tools / viewer — к разговору о видимости перед группой B
- «Resolved (0) — ответ; пропавший раздел читается как сломанная страница». Правило для нашего отчёта: пустой раздел показывать с нулём, не прятать. Проверить наш report.html.
- «Файл без замечаний — успех только при task_done; ошибка — отказ, наряженный тишиной». Их формулировка нашего принципа.
- у каждой строки списка сессий ссылка «сравнить с предыдущим» — прямой ответ на «стало лучше или хуже».
- отметки Fixed/Ignored у каждой находки, спрятать отмеченные — работа человека со списком.
- ДЫРА-КАНДИДАТ (их): task_done{state:FAILED} не сохраняется и не влияет на код возврата. Проверить в коде.
- честная оговорка у них: прогон без манифеста → Resolved вместо Not reviewed (ложное «исправлено»).

## examples/github_actions/README — ГИПОТЕЗА №1 почти снята
- «checks out the trusted base and fetches only the head's blobs» под pull_request_target; «do not point rule at PR-sourced file». Проверить в action.yml, откуда .opencodereview/rule.json.
- ОБРАЗЦЫ ДЛЯ НАС:
  * checkpoint_range: fail-closed («when in doubt, full range»), причина отказа всегда в выходе (range_reason) — у нас «проверка не состоялась» с причиной; «widen-only»; двигается лишь после complete; «complete = выбранное, не каждый байт» — честная граница обещания.
  * resolve_outdated: «модель промолчала — не доказательство, что находки исчезли»; режим report до true.
  * «наш конвейер этот путь не проходит — не читайте его прогоны как доказательство» — ровно наш «готово = доказано».
  * замер прав токена на трёх заданиях вместо веры в viewerCanResolve.
- ПРОТИВОРЕЧИЕ У НИХ: verify-action-pins.sh держит SHA внутри action.yml, а пример пользователю — @main и create-github-app-token@main. Наш deps-are-pinned это ловит? проверить.
- утверждение «env: на шаге uses: составного действия молча игнорируется» — проверить снаружи (документация GitHub), возможный класс «настройка молча не доходит».
- утверждение «sticky_summary без кавычек не совпадёт» — сомнительно (входы действий всегда строки) — проверить.

## examples/gitlab_ci/README — ЖИВОЙ ОБРАЗЕЦ «не состоялась ≠ чисто»
- обёртка «пропустить, если уже ревьюили»: любое упоминание слова OpenCodeReview в заметках → exit 0 навсегда; код возврата ocr не проверяется, «completed» печатается всегда. Кандидат в письмо (документация, воспроизводится чтением). Проверить, есть ли тот же код в .gitlab-ci.yml самого примера.
- хорошее: OCR_FAIL_ON_SEVERITY — порог валит задание ПОСЛЕ публикации сводки (видимость сохранена); счётчики inline/summary/routed/skipped/failed взаимоисключающие и в сумме дают total — инвариант, который можно проверять машиной. У нас: в отчёте суммы сходятся? (ok+fail+cannot = всего).
