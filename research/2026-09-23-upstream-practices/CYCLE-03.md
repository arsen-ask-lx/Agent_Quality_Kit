### Форкнуть их и приделать AQK? — решение владельца 2026-09-26: не форкаем

Рекомендация: **нет, не форкать; брать решения и встать рядом.** Причины:

1. **Разные вопросы.** OCR спрашивает модель «что не так в этом дифе» — ответ меняется от прогона к прогону и стоит токенов. AQK доказывает программой, что защита ловит брак, — ответ воспроизводим. Наш свод прямо запрещает вердикт, который выносит модель (`PROJECT.md` §2, отличие от Exadel). Форк сделал бы AQK ещё одним ревьюером на модели.
2. **Не удержим форк.** У них 89 выпусков за два месяца и команда Alibaba; 945 файлов на Go против нашего правила «читается глазами за один присест, без зависимостей». Форк отстанет за неделю.
3. **Вместе они сильнее, чем слитые.** OCR ищет беду в дифе; AQK проверяет, что обвязка вокруг него не молчит: например, что конвейер не считает `exit 0` при непроверенных файлах успехом. Это заявка в каталог по итогам чтения кода, а не форк.
4. **Лицензия форк разрешает** (Apache-2.0), дело не в ней.

### Находка 1 — неудача общего предка превращается в «✅ пропущено» (подтверждено)

Цепочка в `action.yml` на `486022d`:

1. стр. 432: `git fetch origin "${BASE_REF}" 2>/dev/null || true` — ошибка получения базы глушится;
2. стр. 433: `MERGE_BASE=$(git merge-base "origin/${BASE_REF}" "${HEAD_SHA}" 2>/dev/null || echo "${HEAD_SHA}")` —
   неудача подменяется самим проверяемым коммитом;
3. стр. 973: `--from "${RANGE_FROM:-$MERGE_BASE}" --to "${HEAD_SHA}"` → диапазон `HEAD..HEAD`, пустой;
4. живой прогон `ocr review --from $H --to $H --format json`: `status: "skipped"`, `terminal_state: "skipped"`,
   `coverage` пустая, **код 0**;
5. `scripts/github-actions/post-review-comments.js:297-299`: при нуле замечаний публикуется
   «✅ **OpenCodeReview**: Review skipped: no items were selected.» — задание зелёное.

Итог: PR с настоящими изменениями получает зелёную галочку ревью, которого не было. Текст честно говорит
«skipped», но знак и цвет задания — «всё хорошо», и ни `status`, ни `coverage` действие не смотрит.
Их же руководство (`examples/github_actions/README.md`, Troubleshooting) обещает ошибку «Cannot find
merge-base» — после строки 433 она появиться не может. Смягчение: чекпойнт не сдвигается, так как
`terminal_state` не `complete`.

Не проверено: как часто на деле падает `merge-base` при `fetch-depth: 0` (удалённая база, сбой сети,
`base_ref` с опечаткой во входе). Кандидат в письмо — решение за владельцем.

Проверено и снято: «два JSON в выводе при провале» — вторая копия шла в stderr; при провале всех файлов
код 1 и один документ, как в документации.

Их тесты этого места не видят: контрактный набор составного действия
(`scripts/github-actions/action-contract.test.js`, 49 проверок, гоняет настоящие шаги `action.yml` с
поддельными `git`/`ocr`) проверяет шаг «Fetch PR head» только с `git`, который всегда успешен, а шаг
«Compute merge-base» в набор не входит вовсе. Для письма удобно: у них уже есть обвязка, в которой такой
тест пишется в десять строк.

### Замер — тесты по умолчанию не смотрит никто

### Находка 2 — частичный провал с нулём замечаний публикуется как «✅» (подтверждено прогоном целиком)

Цепочка на `486022d`:

1. `internal/session/manifest.go:941-958` — `computeTerminal`: часть выбранных файлов упала → `partial`;
2. `cmd/opencodereview/review_cmd.go:330-340` — договор кода возврата записан словами: «любое покрытие,
   даже неполное, — выход 0; complete/partial/skipped успешны, ненулевой только failed»;
3. `cmd/opencodereview/output.go:616` — сообщение «Review partially complete: 0 finding(s); N of M selected
   item(s) failed.»;
4. `scripts/github-actions/post-review-comments.js:297-304` — при нуле замечаний сводка
   «✅ **OpenCodeReview**: <сообщение>», без списка предупреждений; задание зелёное.

Итог: «9 из 10 файлов не проверены» приходит в PR с зелёной галочкой. Текст честен, знак и цвет — нет.

**Живой прогон, 2026-09-26.** Поддельная OpenAI-совместимая модель (`OCR_USE_ANTHROPIC=false` — без него `ocr`
говорит по протоколу Anthropic, отсюда первая неудача опыта): на запрос с `<file path="b.go">` — ошибка 400,
на остальное — `task_done`. Два файла по 110 строк (чтобы группировка шла по файлу). `ocr` v1.12.9:
код **0**, `status: "partial"`, «Review partially complete: 0 finding(s); 1 of 2 selected item(s) failed.»,
ключа `warnings` в JSON нет. Этот JSON скормлен их настоящему `post-review-comments.js` с поддельным GitHub:
опубликовано ровно

    ✅ **OpenCodeReview**: Review partially complete: 0 finding(s); 1 of 2 selected item(s) failed.

а выходы действия — `comments_total 0, comments_failed 0`: и последующий шаг, гейтящий по `comments_failed`,
не увидит ничего. Тот же прогон скрипта на ответе из находки 3 опубликовал
«✅ **OpenCodeReview**: Review skipped: no items were selected.».

В `post-review-comments.test.js` 166 проверок, и они строгие к доставке: лимиты, повторы, пересечение
замечаний, инвариант «inline + summary + skipped + failed + routed == total». Ни одна не смотрит на
`status` обзора: что публикуется, когда сам обзор частичный или пропущен, тестами не закреплено никак.

### Находка 3 — слишком большой файл превращается в «✅ пропущено» без причины (подтверждено прогоном)

`internal/agent/agent.go` (`Run`): файл, чей дифф больше 80 % `max_tokens`, получает `too_large` ещё до
выбора; если так отсеяно всё, прогон завершается `skipped` без `run_failure`. Причина пишется только строкой
прогресса в stdout — под `--audience agent` (режим по умолчанию в их действии и скиллах) её нет.

Живой прогон `ocr` v1.12.9: правка в один файл, `--max-tokens 500` → код **0**, `status: "skipped"`,
`message: "Review skipped: no items were selected."`, `coverage.selected` пуст; слов `too_large`/`exceeded` нет
ни в JSON, ни в stderr. В их действии это становится «✅ **OpenCodeReview**: Review skipped: no items were
selected.» (та же ветка `post-review-comments.js:297-304`, что в находке 1).

Условие в жизни: дифф одного файла больше ~160 тыс. токенов при умолчании 200 тыс. — сгенерированный код,
большой JSON, вендорный файл под непривычным путём. Отличие от находки 1: не нужен никакой сбой, достаточно
размера. Смягчение: `--preview` называет `too_large`, но в конвейере его никто не запускает.

### Находка 4 — пропавший файл командных правил молча заменяется встроенными (подтверждено прогоном)

`internal/config/rules/system_rules.go` (`resolveRuleEntries` → `tryReadRuleFile`): правило проекта вида
`{"path":"**/*.go","rule":"docs/team-go-rules.md"}`, чей файл не найден, получает пустой текст — строка в stderr
«WARNING: rule file not found», — а `matchProjectRuleEntry` пропускает пустые записи, и файл уходит на
встроенное системное правило. Прогон v1.12.9: `ocr rules check a.go` → «Source: System built-in», код 0;
`ocr delegate rule --format json` → `"source": "system"`. Ревью идёт не по тем правилам, что велела команда, а
в конвейере (`--audience agent`) предупреждение остаётся только в журнале stderr. Слабее находок 1–3: есть
предупреждение и есть способ проверить (`rules check`, поле `source`); но никто его не вызывает сам. Класс AQK —
«проверили не то, что человек велел, и не сказали» (как наш мусорный предел гейта).

### Находка 5 — изменённый файл под `.gitignore` исчезает бесследно, `--preview` говорит «No files changed» (подтверждено прогоном и замером)

`internal/diff/git.go`, `partitionDiffs`: изменение тянется из git (`git diff`/`git show`), а затем каждый файл
сверяется с корневым `.gitignore` их собственным разбором; подходящий файл не попадает ни в `Included`, ни в
`Excluded` — комментарий к `ForEachInOrder` прямо говорит «Files dropped by .gitignore are not visited». Но
`.gitignore` действует только на неотслеживаемые файлы: файл, добавленный через `git add -f` или закоммиченный
до появления правила, git отслеживает и показывает в дифе.

Прогон `ocr` v1.12.9: `.gitignore` = `*.sql`, `config/local/`; в git лежат `db/001_init.sql` и
`config/local/app.yaml`; коммит дописывает `DROP TABLE users` и `password: hunter2`. `git show --stat` — 2 файла.
`ocr review --commit HEAD --preview` → **«No files changed.»**; `ocr review` → `status: skipped`,
«Review skipped: no items were selected.», код **0**; в их действии — «✅ Review skipped». Их же диагностика
говорит, что изменений нет.

Замер, 2026-09-26: `git ls-files -ci --exclude-from=.gitignore` (отслеживаемые файлы, подходящие под корневой
`.gitignore`) на 36 локальных клонах открытых репозиториев — **у 8 из 36 такие файлы есть** (1–35 штук): среди
них `.claude/settings.json`, `.vscode/launch.json`, `scripts/report-editor-latest-json-hits.sh`,
`package-lock.json`, `packages/devtools/.env`, `testdata/*.json`. Любая правка этих файлов для OCR не
существует. Замер — по правилам git, а не по их разбору (он ещё и читает только корневой `.gitignore`), так что
это оценка, а не точное число.

Отличие от находок 1–3: здесь не «пропустили с пометкой skipped», а «изменений нет» — и в предпросмотре тоже.

Их тесты это закрепляют, а не ловят: `internal/diff/gitignore_test.go` (`TestIsPathExcluded_AllowListGitignore`)
на идиоме `github/gitignore` Go.AllowList (`*`, затем `!*.go`, `!go.mod`…) требует исключить
`internal/testdata/fixture.yaml` — то есть в таких репозиториях правки `Dockerfile`, `Makefile`, YAML-конфигов,
лежащих в git, для OCR не существуют. Ни один тест не различает «отслеживается git» и «не отслеживается». При этом их же правило сформулировано дословно в
`internal/diff/quotedpath_test.go`: «a changed file must never be silently omitted» — и за ним история починок того
же класса (пути в C-кавычках, имена с пробелами, сбой `git ls-files`, маркер `Binary files` в тексте, allow-list
`.gitignore`, при котором «a review silently covered nothing»). Находка 5 — ещё один случай их собственного
класса; для письма это лучшая опора.

**Уточнение после чтения `git_test.go`: это задумано.** `TestGetDiffSetWalksChangesetOrderAcrossGitignoreDrop`
прямо пишет «skip.log is tracked so git diff still emits it; partitionDiffs then drops it» и требует, чтобы
отброшенный файл не был показан вовсе — в отличие от `vendor/`, который они показывают как `provider_directory`.
Значит, подача для письма — не «у вас баг», а «вы уже показываете исключённое по каталогам с причиной; покажите
так же отслеживаемые файлы, отброшенные по `.gitignore` (причина `gitignore`), и не пишите "No files changed",
когда git видит изменения».

### Находка 6 — сравнение с прогоном, убитым на середине, объявляет непроверенное «исправленным» (подтверждено прогоном)

`ocr session compare <до> <после>` раскладывает замечания по четырём корзинам, и корзина «не смотрели»
(`not_reviewed`) существует ровно затем, чтобы файл, до которого второй прогон не дошёл, не считался
исправленным. Их собственный комментарий к `ReviewedPaths` (`internal/session/compare.go`): «Selected is
deliberately not used — it is the intended set, so an interrupted run would report every file it never got to as
clean». Но список просмотренных берётся из манифеста, а манифест пишется только в последнюю запись журнала,
`session_end`. У прогона, убитого жёстко (`kill -9`, нехватка памяти, таймаут конвейера, упавшая машина),
`session_end` нет, манифест `nil`, и `Compare` для `nil` делает то, что задумано для старых сессий: всё
несовпавшее — «Resolved».

Прогон `ocr` v1.12.9 с подставной моделью, два файла, в каждом одно замечание:

| прогон «после» | `session list` | `session compare` |
|---|---|---|
| прерван Ctrl+C | `failed` | 1 persisting, **1 not reviewed** — честно |
| сам обозреватель (`opencodereview`) убит `kill -9` после a.go | `aborted`, и через 20 с тоже | 1 persisting, **1 resolved** (b.go), предупреждения нет, код 0 |

Поправка к способу, 2026-09-26: в первом прогоне я убил `kill -9` обёртку npm, а не обозреватель. Сам
обозреватель продолжил работу и позже дописал конец журнала, так что сравнение шло с ещё идущей сессией.
Результат тот же, но это был другой случай. Повторено честно: убит сам процесс `opencodereview`, обёртка
вернула 137 (смерть от сигнала передана верно), сессия осталась `aborted`, а сравнение то же.

То есть одна и та же программа в `session list` знает, что прогон оборван, а в `session compare` выдаёт
непросмотренный файл за исправленный. `--json` даёт то же: `resolved: ['b.go'], not_reviewed: []`. Веб-просмотр
(`internal/viewer/handler.go`, `handleCompare`) вызывает `Compare` так же и тоже ничего не проверяет.
Сведения, чтобы ответить честно, в журнале есть: у убитого прогона лежат чекпойнты `review_item_done` по
законченным файлам.

Тест `TestReviewedPaths` закрепляет «nil — всё несовпавшее в Resolved» как решение для сессий старше
манифестов; оборванная сессия нового формата под это решение попала случайно.

Самое точное место для письма: у них есть тест ровно с этим намерением —
`TestRunSessionCompare_UnfinishedAfterRunIsNotResolved` (`cmd/opencodereview/session_cmd_test.go:793`). Но
«unfinished» там — прогон, который **закрылся** с манифестом `failed` и файлом в `Coverage.Failed`. Прогон,
который **не закрылся вовсе**, идёт другой веткой (манифеста нет) — её тест не касается. Код сравнения в их
текущей ветке (`486022d`) тот же, что в опубликованной 1.12.9. Подача для письма: «для
`Aborted` сессии берите просмотренные файлы из чекпойнтов или откажитесь сравнивать — как уже отказываетесь
при разных репозиториях».

**Для AQK это прямой урок.** Мы начали хранить историю прогонов, чтобы показывать «стало лучше или хуже»
(§9а). Прогон без записи о завершении обязан сравниваться как «не состоялся», а не как «ничего не нашёл».

### Находка 7 — закреплённая версия не держится: обёртка npm сама ставит последнюю, и посреди замены команды нет (подтверждено прогоном)

Их README действия (`examples/github_actions/README.md:29`): «Pinning only the Action reference therefore does
**not** freeze review behavior … For a fully reproducible setup, pin both: `ocr_version: 'X.Y.Z'`». Действие
ставит эту версию `npm install -g …@${OCR_VERSION}` (`action.yml:544`) и сразу зовёт `ocr version`. Но обёртка
npm (`bin/ocr.js`) при каждом запуске, если с прошлой проверки прошло 18 минут, отцепляет в фон
`scripts/update.js`, а тот, найдя в реестре версию новее, делает `npm i -g <пакет>@<последняя>`. Отключается
это только `OCR_NO_UPDATE`, а действие его не выставляет. В документации поведение описано
(`installation.md:25`, «upgrades automatically»), так что это не скрытое свойство. Скрытое другое: оно
отменяет закрепление, которое их же README советует.

Прогон в песочнице (свой префикс npm и свой HOME), та же последовательность, что в действии: установить
1.12.7 → `ocr version` → десять `ocr config set` → через 20 с `ocr version`:

| | с обновлением (как в действии) | контроль, `OCR_NO_UPDATE=1` |
|---|---|---|
| версия после установки | 1.12.7 | 1.12.7 |
| вызовов `ocr config set` с кодом **127** («command not found») | **6 из 10** | 0 из 10 |

### Находка 9 — расширение VS Code пишет «No issues found · Passed» на частичный обзор; расширение IDEA то же правило уже исправило (подтверждено на настоящем выводе)

`extensions/vscode/src/extension/services/ReviewSession.ts`, `resultToState`: есть замечания — «done»;
статус `completed_with_errors` — «failed»; **всё остальное — «empty»**, а «empty» рисуется как
`view.empty.noIssues` = «**No issues found · Passed**» (по-русски «Проблем не найдено · Проверка пройдена»).
Но `ocr review --format json`, который расширение запускает (`cliParse.ts:14`), отдаёт статусы манифеста —
`complete`, `partial`, `failed`, `skipped`; `completed_with_errors` бывает только у `ocr scan`. Та же функция на
моём настоящем JSON частичного прогона (1 из 2 файлов упал, код 0): `status=partial → empty → «No issues
found · Passed»`. Полный провал сюда не доходит — при коде 1 расширение само уходит в «failed». Тест
(`__tests__/ReviewSession.test.ts:15`) закрепляет `skipped → empty`, то есть находки 1, 3 и 5 в VS Code тоже
выглядят как «Passed».

Расширение IDEA решает ту же задачу правильно (`idea/.../services/ReviewSession.kt:18`): «Only recognized,
non-failing terminal results can report an empty review» — незнакомый статус и `partial`/`failed` дают FAILED.
Это два исполнения одного правила, разошедшиеся между собой, и общего теста-договора на них нет (общий у
расширений только веб-интерфейс, и его тип `CliResult.status` знает лишь `success | completed_with_errors |
completed_with_warnings | skipped` — статусов манифеста в нём нет вовсе). Для письма это лучший случай из
всех: исправление уже написано ими же, его надо перенести из Kotlin в TypeScript.

**Для AQK урок про нас самих:** одно правило в двух местах расходится молча. У нас так живут, например,
каталоги строк на двух языках — их сторожит модульная проверка; других пар без сторожа надо поискать.

### Образец для AQK — учёт покрытия (`internal/session/manifest.go`, прочитан целиком)

- знаменатель запечатывается до начала работы: после `SealSelected` добавить файл в «выбранные» нельзя;
- у каждого файла ровно один итог; конфликтующая повторная запись — ошибка, а не молчаливое «первое победило»;
- файл без записанного итога при закрытии сам становится `failed` с причиной «no terminal outcome recorded»;
- закрытие проверяет инвариант `selected = completed + reused + failed + waived`, иначе манифест не выпускается;
- «отменено человеком» (`waived`) без причины — ошибка;
- итог прогона считается только из покрытия, «никогда из числа замечаний или предупреждений».

Ещё из `internal/session` (прочитан целиком, код и тесты):

- сессия считается оборванной, пока не прочитана запись о завершении (`Aborted: true` по умолчанию) —
  отсутствие конца не выдаётся за конец;
- продолжение прерванного прогона допускается, только если совпало всё, что определяет вход: хэш отобранного,
  хэш правил и фильтра, репозиторий; смена модели или провайдера, пришедшая не флагом, а из конфига или
  окружения, отвергается — «неявный переход и есть то, что эта проверка ловит»;
- пустое с пустым не сравнивается: родитель без отобранных файлов отвергается, иначе два пустых хэша
  совпали бы и «прошли» все сверки;
- повторный вызов закрытия отдаёт ту же ошибку, что и первый, а не «успех»
  (`TestFinalizeReplaysWriteErrorOnEveryCall`);
- имена тестов — утверждения: `MissingSessionIsReportedNotSilentlyIgnored`,
  `ReportsAStatFailureRatherThanSkippingIt`.

Из `scripts/github-actions/check-plugin-contract.js` — лучший у них образец нашего принципа:

- **пол корпуса**: проверка ссылок падает, если нашла меньше 50 ссылок в 10 файлах — «a check that finds
  nothing must fail rather than report success»; реальный корпус 146 ссылок, пол взят заведомо ниже;
- документ, который не удалось прочитать, называется поимённо («its in-repo links were NOT verified»), а не
  выпадает из счёта;
- допущение, которое проверка не может подтвердить (как Cursor разрешает пути), печатается предупреждением
  **при каждом прогоне** («Silently passing would be worse than either outcome»);
- пустое дерево навыков или команд — ошибка («installs cleanly and exposes nothing»);
- проверка гоняется и на push в main: два PR по отдельности зелёные, а вместе ломают инвариант.

Для AQK: у сканирующих гейтов пола корпуса нет — проверить, что говорит гейт, когда обход нашёл ноль файлов
своего типа: «чисто» или «не смотрел».

Для AQK: то же для `doctor --run` — объявленные гейты = ok + fail + cannot (+ пропущенные с причиной), гейт без
итога сам становится «не состоялась», инвариант проверяется до записи отчёта. Сверить с `tool/lib/run.mjs`.

### Граница OCR и AQK — по их же правилам (прочитаны все 55 файлов `rule_docs`)
