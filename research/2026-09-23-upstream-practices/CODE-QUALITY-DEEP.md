# code-quality: механизмы, испытания и условия переноса

Дата: 2026-09-23. Снимок: `smixs/code-quality@407501608b1ffe8ab0e236b742513592fca9ed60`.
Это второй проход исследования: исходники → их вызывающий код → тесты → независимые пробы.
Пофайловый проход этого снимка завершён: 91 текстовый файл прочитан целиком (466 836 байт),
11 обёрток побайтово равны прочитанной (12 320 байт), 3 графических ресурса проверены отдельно
(28 006 байт). Все 105 записей и содержательные заметки — в [журнале](CODE-QUALITY-FILES.md).
Это завершённое чтение одного источника, не всего корпуса и не доказательство работы всех интеграций.

## 1. Что именно было выполнено

[Воспроизводимый скрипт](evidence/code-quality-probes.mjs) импортирует настоящие экспортированные
функции из скачанного снимка. [Результат — 13 наблюдений](evidence/code-quality-probes.json).
Среда: Node.js 22.23.0 с удалением TypeScript-типов. Дополнительные пакеты не устанавливались.

```sh
node --experimental-strip-types research/2026-09-23-upstream-practices/evidence/code-quality-probes.mjs
```

Временные репозитории создаются под `/tmp`, локальные коммиты нужны только фикстуре;
хуки в них выключены через параметр отдельного git-процесса. Настройки AQK и пользователя
не меняются. Скрипт убирает свои временные папки.

Для протокола используется подставной исполняемый `bun`, выдающий заранее заданный ответ.
Для LCOV используется синтетический writer. Это **не** полная проверка Bun CLI, не реальный
прогон тестируемого приложения и не интеграция с Pi/OMP. Проверяется конкретная семантика
границ: что общий адаптер делает с неверным ответом и когда функция считает LCOV свежим.

Две первые попытки самого исследовательского скрипта не завершились: неверный относительный
путь к клону, затем обращение автообнаружения языков к Bun.Glob. Исправлен путь; опыт порога
перенесён в отдельный пустой Git-репозиторий, где glob не нужен. Третья попытка завершилась
с кодом 0. Ошибки исследовательского стенда не записаны как дефекты upstream.

## 2. Подтверждённые пробами ограничения

### CQ-01. Неисправный ответ guard может разрешить действие

Источник: [invoke.ts:6–26](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/adapters/invoke.ts#L6),
потребители — [Pi](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/adapters/pi.ts)
и [OMP](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/adapters/omp.ts).

Механизм: `invoke` сохраняет `code=0`, `output=null` и текст ошибки парсинга. `denied` проверяет
поле deny и код процесса, но не сам факт ошибки протокола. Потребитель проверяет truthiness
возвращённой причины.

| Ответ подпроцесса | Код | Наблюдение общего адаптера |
|---|---:|---|
| `{}` | 0 | Разрешает, корректный зелёный контроль |
| `not json` | 0 | Разрешает, хотя `error` содержит invalid JSON |
| `null` | 0 | Разрешает при `output=null` |
| deny с непустой причиной | 0 | Блокирует, красный контроль |
| deny без причины | 0 | Возвращает undefined; проверка причины не блокирует |
| неверный JSON | 2 | Блокирует по ненулевому коду |

Предел: штатный guard-bash при своём deny печатает причину и выходит 2; опыт не утверждает,
что он обычно генерирует неисправный ответ. Дефект относится к обработке **аварийного протокола**.
Другой адаптер, OpenCode, реализован отдельно и отклоняет ошибку JSON. Stop-пути Pi/OMP также
отдельно проверяют отсутствие output; нельзя распространить находку на все точки входа.

Для AQK: проверять код процесса **и** схему ответа; `allow`, `deny`, `cannot` должны быть
явными состояниями, а текст причины — их пояснением. Пустая причина не отменяет deny.
До переноса нужен тот же набор контрольных ответов на фактическом установленном клиенте.

### CQ-02. Свежесть LCOV не включает всю проверяющую среду

Источник: [crap.ts:41–117](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/crap.ts#L41).
Отпечаток: git diff от сохранённого коммита только по `o.dirs` плюс содержимое untracked
в этих каталогах. Команда теста, внешние тесты, зависимости, версия инструмента не включены
как самостоятельные входы.

Фикстура задаёт `dirs=['src']`. Сначала создаётся LCOV с одним покрытым исходным файлом.
Без изменения исходника последовательно меняются тест в `tests/`, корневой `package.json`
и команда теста на `exit 1`. После каждого шага `fresh-or-none` возвращает `used=true, red=false`.
После изменения `src/value.js` возвращает `used=false` — контроль чувствительности работает.

Предел: синтетический writer доказывает решение о **повторном использовании**, а не реальное
процентное покрытие. Если `src=['.']` и нужные файлы tracked, значительная часть риска исчезает;
не следует заявлять, что каждый запуск этого инструмента использует устаревшие данные.
Последовательные изменения в опыте накопительные; данные не являются отдельным benchmark каждого.

Для AQK: при кэшировании включать код, проверяющие тесты, конфиги, lockfiles, команды, версии
инструментов и фактическую область. Свидетельство относится к одному состоянию входов;
последующий отчёт не может сделать старый запуск новым. [evidence.mjs](../../tool/lib/evidence.mjs)
уже хеширует base, команды и переданные файлы. Это полезный строительный блок, но полный
набор входов определяет вызывающий код, а не сама hash-функция.

Дополнительно сверено [report.mjs:95](../../tool/commands/report.mjs#L95): AQK **сам запускает**
гейты перед построением отчёта. Подозрение, что report просто приписывает старым результатам
новый hash, этим чтением не подтвердилось. Этот отвергнутый ход сохранён, чтобы не расследовать
его повторно на основании одной вырванной строки.

### CQ-03. Нечисловой порог CC принимается как NaN

Источник: [config.ts:130](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/config.ts#L130),
[gate.ts:97](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/gate.ts#L97).
`buildOpts(readArgs(... --max-cc not-a-number))` успешно возвращает `maxCc=NaN`.
Проверка `100 > maxCc` ложна. Реальный `complexityReason` использует именно `f.cc > o.maxCc`.

Это подтверждает принятие неверной настройки и выключение сравнения CC. Полный GATE PASS
не проверялся: другие правила могут независимо заблокировать изменение. Про `--max-crap`
нельзя сделать такой же вывод по аналогии: его сравнение написано иначе.

Для AQK: валидировать тип, конечность и диапазон **при чтении настройки**, до запуска
инструментов. Красные контроли: строка, NaN/Infinity там, где парсер допускает, отрицательное
значение, недопустимая доля покрытия. Не превращать ошибку настройки в хороший результат.

### CQ-04. Объявленный pin не гарантирует версию уже заполненного кэша

Источник: [crap.ts:150–175](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/crap.ts#L150).
`ensureTools` проверяет существование package.json, не читая его version. В фикстуре пакет
`fictional-tool` имеет version 1.0.0. Вызов `ensureTools(['fictional-tool@9.9.9'])` возвращается,
оставляя 1.0.0. Никакой сетевой установки не происходит.

Кроме того, `loadEslint` сначала пробует установленный в целевом проекте ESLint/parser.
Это может быть осознанной совместимостью с проектом, но ослабляет утверждение о едином
закреплённом анализаторе. Часть native tools в tools.ts вообще берётся из PATH.

Для AQK: в отчёте нужны **фактически использованные** имя/версия/путь инструмента, а не только
конфигурационный pin. Кэш либо адресуется набором версий, либо проверяется перед использованием.
Один pin верхнего npm-пакета также не фиксирует все транзитивные зависимости.

### CQ-05. Ошибка анализатора теряется, если он успел вывести известную находку

Источники: [adapter-tools.ts:176–187](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/adapter-tools.ts#L176),
[acceptedResult:231](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/adapter-tools.ts#L231),
[ratchet:461](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/adapter-tools.ts#L461).

`acceptedResult` принимает любой код процесса, когда удалось разобрать хотя бы одну находку.
После этого `check` создаётся без error, stderr теряется. Если находка уже в baseline,
`ratchetAdapterChecks` удаляет её, оставляя результат без findings и без error.

[Независимый скрипт](evidence/adapter-failure-probes.mjs) передаёт реальным экспортированным
функциям результаты подставного анализатора. [Сохранённый вывод](evidence/adapter-failure-probes.json):

| Вход | Находок после обработки | Ошибка |
|---|---:|---|
| exit 0, `[]` | 0 | нет — зелёный контроль |
| exit 2, `[]`, stderr с аварией | 0 | сохранена — аварийный контроль |
| exit 0, известная находка | 1 | нет — контроль парсинга |
| exit 2, та же находка и stderr с аварией | 1 | **нет** |
| предыдущий результат после baseline | **0** | **нет** |

Доказано поведение общей границы адаптера. Не утверждается, что конкретный установленный Ruff
или другой анализатор обязательно печатает такой JSON перед аварией. Допустимые exit codes
должны задаваться договором каждого инструмента; правило «есть хоть одна находка — всё прочее
неважно» этот договор не выражает. Полный gate со всеми остальными проверками здесь не запускался.

Для AQK: хранить независимо **находки**, **завершённость проверки**, **ошибку процесса**.
Фильтрация старого долга не должна стирать признак несостоявшегося полного анализа.
Красный пример обязателен именно после baseline: до него уязвимость маскируется красной находкой.

### CQ-06. Поздний сбой OSV стирает уже найденную уязвимость из общего результата

Источник: [adapter-tools.ts:76–92](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/adapter-tools.ts#L76).
Цикл накапливает успешные scans, но при следующем `scan.check` сразу возвращает только этот check.
Ранее собранные findings не входят в возвращаемое значение.

Фикстура содержит `package-lock.json` и `z/Cargo.lock`. Настоящий `git ls-files` определяет файлы
и порядок; runner OSV подставной. Для первого файла он возвращает JSON с `FIXTURE-ONLY-001`;
это заведомо вымышленный идентификатор, не реальная опубликованная уязвимость.

- Контроль: второй файл проверен без находок → итог содержит одну находку и две просканированные
  package-единицы по stderr фикстуры.
- Аварийный сценарий: второй файл вернул exit 2, пустой stdout и `unable to fetch OSV database` →
  итог содержит **0 находок**, пустой error и notice `not run: deps/audit (OSV database unavailable)`.

Это не утверждение о полном зелёном приложении: notice остаётся видимым, а другие гейты независимы.
Проблема в потере уже установленного факта. Для AQK известный брак должен сохраняться рядом
с неполнотой проверки: «найдена уязвимость в A; B проверить не удалось». Общий результат не может
улучшаться от добавления ещё одной проверки, которая закончилась ошибкой. Полезный инвариант
для property-based проверки будущего агрегатора: добавление cannot не удаляет известный fail.

## 4. Осознанные политики, которые нельзя спутать с универсальными гарантиями

**Stop разрешает закончить после одного повторного красного результата.**
[hooks.ts:440](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/hooks.ts#L440)
хранит пару session + deterministic verdict. Повтор даёт systemMessage без `decision:block`.
`pipeline.test.ts:177–199` требует такого поведения. Это защита от бесконечного цикла, а не дефект
самого контракта. Обязательная финальная приёмка должна существовать независимо от stop.

**Отсутствие инструмента может оставлять зелёный код.** `lang-fixtures.test.ts:37–60` специально
ожидает exit 0 с сообщениями not run. Это политика optional tools. Для AQK нельзя выдавать её
за выполнение обязательного гейта; SPEC различает несостоявшуюся проверку и успех.

**Изменённые файлы не равны всему влиянию изменения.** `dup.ts:25` передаёт jscpd только changed
files, поэтому сравнение с неизменённым файлом не гарантировано. Pre-push выбирает тесты по
именам и прямым TS-импортам, с максимумом 40 и сообщением omitted. Это сокращённая проверка,
не транзитивный impact analysis и не обещание полного набора.

**Защита от изменения тестов эвристическая.** `tamper.ts` считает строки assertions внутри
hunk, сопоставляет первые аргументы собственным разбором скобок, узнаёт переименование теста
по двум общим словам либо одному длинному. Такой механизм не доказывает логическую силу
утверждения и может ошибаться на переносе тестов/комментариях/строковых литералах.
Для AQK с собственными анализаторами строк особенно нужен независимый корпус законных изменений.
Все 619 строк `tamper.test.ts` прочитаны: есть контроли законного переименования, переноса
части assertions, строк/docstrings и unrelated suppressions. Это уменьшает неопределённость
о намерении автора, но не доказывает полноту синтаксического покрытия или отсутствие ложных отказов.

**Область защищённых настроек конечна.** `PROTECTED_CONFIG` в tamper.ts включает src/thresholds/
часть hooks/security/review; там нет всех полей project и tools. Изменение настройки отдельным
коммитом разрешено политикой. Это не универсальная гарантия, что агент не изменил приёмку.

**Поиск текстовых тестов требует контекста.** AST-rule может справедливо найти тест, читающий
исходник вместо вызова поведения. Но для инструмента анализа исходников текст — нормальные
входные данные. Нужна проверка того, что именно тестируется, а не запрет чтения файлов вообще.

## 5. Исправление первоначального пересказа документации

[limits.md:31](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/skills/code-quality/references/limits.md#L31)
говорит о неработающем первом коммите и предлагает no-verify. Однако `diff.ts` имеет headOrEmpty,
`hook-chain.md` описывает пустое дерево, а `pipeline.test.ts:135–143` ожидает обнаружение CC 12
на первом staged commit. Поэтому прежний пересказ limits нельзя считать актуальной оценкой
хуков. Подтверждено расхождение документации с кодом/тестом; собственного Bun-прогона этого
сценария ещё нет. Полный запуск с coverage — отдельный путь: runFresh всё ещё требует HEAD.

## 7. Дополнения после полного чтения security, адаптеров и LLM-части

**Два auditCheck — разные пути.** Экспорт `security.ts:392` кэширует npm-аудит по lockhash/tool,
без срока актуальности базы уязвимостей. Но поиск импортов в снимке показывает его только
в security.test.ts; gate использует `adapterChecks` из adapter-tools.ts. Поэтому вывод
«действующий аудит всегда использует бессрочный кэш» был бы неверным. Это пример, почему
читаем реализацию вместе с вызывающим кодом, а не превращаем подозрительную функцию в баг продукта.

**Baseline — политика принятия долга.** При `known === null` все adapter-findings снимаются,
а в notices предлагается пересоздать baseline. Тест требует именно этого. В ключах обычного
baseline присутствуют строка и сообщение: без изменения логики перенос строк может выглядеть
новой находкой. Для AQK стоит испытать стабильность идентичности долга на изменениях форматирования.
Нужен также явный выбор владельца: допустимо ли переносить старые уязвимости в baseline вообще.

**LLM-рецензия не проверена как измерительный прибор.** jev.test проверяет HTTP-протокол,
не точность ответов. Пять вопросов, короткие hunks и перечень изменённых source-paths не дают
модели полного поведения приложения. Оценки надо проверять на размеченных хороших/плохих
примерах, считать ложные тревоги и воспроизводимость. Сейчас payload содержит тестовый текст
и пути без отдельного redaction, а лог — HEAD без полного diffhash: до включения внешнего
провайдера требуется явная конфигурация отправляемого контекста и версия свидетельства.
Никаких внешних запросов к модели в этом исследовании не выполнялось.

**Парсеры — часть доверенной границы.** SARIF проверяет наличие runs, OSV — results; generic
JSON распознаёт знакомые поля рекурсивно. Неизвестная форма не всегда отличается от пустого
списка. Это кандидат на отдельный корпус повреждённых ответов, не доказанная совместимость
со всеми версиями заявленных анализаторов. Прочитанные fixture-тесты часто запускают
подставные executable: результат нельзя подписывать «Ruff/PMD/Clippy испытаны вживую».

**Оставшиеся гипотезы, не подтверждённые дефекты:** чтение старого SARIF при пустом stdout;
сопоставление исторической gitleaks-находки с allow-marker текущего worktree; unknown JSON
схема при exit 0; неполная область защищённых конфигурационных ключей. Для каждой сначала
нужен договор конкретного анализатора и воспроизведение, затем вывод.

## 8. Приоритет переноса в AQK по результатам этого прохода

| Приоритет | Кандидат | Где сравнить в AQK | Арбитр до внедрения |
|---|---|---|---|
| 1 | Сохранение findings при partial failure | раннер/агрегатор результатов, report | fail(A)+cannot(B) сохраняют оба факта; порядок не меняет вердикт |
| 1 | Честная ошибка недоступной базы diff | kit/gates/test-not-adjusted/check.sh | уже сохранённая missing-base проба + корректный ref |
| 1 | Отпечаток фактически проверенных входов | tool/lib/evidence.mjs и report | изменение теста/команды/config/lockfile лишает старое свидетельство свежести |
| 2 | Корпус законных и недопустимых правок тестов | существующий checkwash gate | независимый общий корпус, precision/recall и объяснимые false positives |
| 2 | Сохранение чужих hooks и индекса | установщик AQK и Git fixture | old hook failure/stdin/worktree/partial staging не теряются |
| 2 | Фактические версии внешних tools | vitals/report, манифест гейта | объявленный pin отличается от установленного → явное несовпадение |
| 3 | Консультативные вопросы jev | отдельный opt-in review-профиль | размеченный набор, стоимость/время, сетевой отказ не меняет строгий вердикт |
| отдельно | UI/нагрузка/observability | профили проектов-получателей | конкретный сценарий и бюджет измерения, не зависимость CLI |

Это предложения для следующего этапа. Код AQK, активные навыки и его конфигурация не изменены.
