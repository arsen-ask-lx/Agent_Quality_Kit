Что это: локальная обвязка вокруг агента. Три части, которые почти не связаны между собой:

1. **Шлюз к модели** (`src/mission-control.mjs`): считает деньги по таблице цен, режет вызовы
   сверх лимита кодом 429, сжимает запросы, ищет зацикливание агента по похожести запросов.
2. **Локальная проверка итога** (`runcap outcome --guard`): до запуска агента снимает отпечатки
   файлов проверки и скриптов `package.json`, после — сверяет и ставит одну из четырёх оценок.
3. **Судья для pull request** (`src/adjudicate.mjs`, `runcap ci --mode adjudicate`): правила и
   проверку берёт из БАЗОВОГО коммита, сам считает диф, накладывает только разрешённые текстовые
   правки на чистую копию базы и прогоняет проверку дважды — до правки и после. Вердиктов три:
   `PASS`, `BLOCKED`, `HUMAN_APPROVAL_REQUIRED`.

Ближе всего к нам третья часть — это `protection-not-removed`, увиденный с другой стороны
(`PROJECT.md` §10).

Косвенно подмену видно: проба внутри `doctor --run` пишет «gate secrets-not-in-code is declared
and was run — and still missed the defect in this file», уровень падает с AQK-2 на AQK-1, а
`prove` называет гейт недоказуемым («the command was written by hand»). Но красного нет, и
причина нигде не названа: **правило поменяли в том же дифе, который это правило судит**.
`protection-not-removed` сторожит только ИМЕНА объявленных гейтов, а не их команды.
`gate-not-weakened` ищет `|| true` и безадресные подавления, а голая команда `true` под ними
не видна.

У Runcap на этом месте правило: диф трогает правила или доказательство — автоматического
вердикта нет, решает человек, и путь назван. Как закрыть это у нас — развилка, решение за
владельцем (ниже).

## Их сильные решения — что стоит взять

- **Прогон до правки обязан упасть.** Судья сначала гоняет проверку на базе. Если она уже
  зелёная, то «зелёное после правки ничего не доказывает» — вердикт `BLOCKED`. Это наше
  железное правило «Красный тест до кода», только у нас его держит человек (`AGENTS.md`, метка
  `aqk: человек`), а у них — программа.
- **Правка правил в том же дифе — решение человека.** Политика, workflow, файл проверки,
  манифест зависимостей, защищённые пути → `HUMAN_APPROVAL_REQUIRED` с названным путём.
  Формулировка из их плана: «a change to the rules cannot be auto-graded by those same new
  rules». У нас та же дыра подтверждена прогоном (см. выше).
- **Судья не берётся из проверяемого PR.** Действие закреплено полным SHA коммита, а не тегом.
  Правила читаются через `git show <base>:путь`. Отчёт агента обязательная проверка не читает
  вообще, даже чтобы показать, — «needless attack surface». Их тест подкладывает поддельный
  `VERIFIED_STRONG` и требует, чтобы вердикт не изменился.
- **Опасные виды правки не принимаются автоматически:** удаление, переименование, символическая
  ссылка, смена режима, подмодуль, двоичный файл, указатель LFS — всё это `BLOCKED` с названной
  причиной.
- **Граница названа в выводе:** `runtime_attestation=not_performed_in_pr_job` печатается в каждом
  вердикте, а их тест требует, чтобы слово `HARDENED` не появлялось нигде. В документации есть
  раздел «What it does NOT prove».
- **Из их плана:** обязательная проверка с `needs:` на задание, которое непроверенный код может
  уронить или пропустить, сама будет пропущена, а пропущенную обязательную проверку можно
  настроить так, что она засчитается как пройденная. Это кандидат в наш каталог про конвейер.
  Каталог заморожен, поэтому сначала замер частоты.

## Что в их коде не сходится с их же заявлениями — по чтению, не прогоном

1. **Приёмка судит по тексту вывода, а не по коду возврата.** `scripts/acceptance.mjs`:
   `run()` отдаёт вывод на `close` и код не смотрит. `mustPass("unit validation", ["npm","test"],
   out => out.includes("Validation passed"))`. `npm test` — цепочка через `&&`, и
   `validate-demo.mjs`, который печатает «Validation passed», стоит в ней четвёртым. Пятый–
   девятый тесты (`outcome`, `guard`, `policy`, `mission`, `adjudicate` — тесты самого судьи)
   могут упасть, строка уже напечатана, приёмка зелёная. Конвейер (`.github/workflows/ci.yml`)
   гоняет только `check` и `acceptance`. **Наш главный класс — проверка, которая не может
   покраснеть, — у инструмента, чья тема — «CI зелёный ещё ничего не значит».**
2. **Неизвестная стоимость считается нулём в лимите.** `readGatewaySummary`:
   `sum + Number(event.cost?.estimatedUsd ?? 0)`. `estimatedUsd` бывает `null` у модели без цены.
   Если ответ не JSON (потоковый ответ, SSE), `safeJson` возвращает `{parseError:true}`, usage
   нет и стоимость тоже `null`. Предварительная оценка: `preCall.estimatedUsd ?? 0` — для
   неизвестной модели лимит пропускает вызов. Если Claude Code ходит через шлюз потоком, лимит,
   похоже, его траты не видит. **Не проверено**: как именно Claude Code шлёт запросы, не
   замерялось.
3. **Проверка, достижимая не напрямую, не защищена.** Файлы проверки берутся только из слов
   самой команды (`verifierFilesAtBase`). При `verify: "npm test"` сам `package.json` уходит
   человеку, а файл, который `npm test` запускает (например `scripts/verify.mjs`), и помощники,
   которых проверка импортирует, — обычная правка кода, если лежат в разрешённой области. При
   пустом `allow` разрешено всё: `validatePolicy` даёт только предупреждение, а судья
   предупреждений не печатает. Их тесты покрывают только проверку, названную в команде прямо.
4. **Пример политики в README не работает так, как написан.** `protect: ["tests/**",
   "package.json"]`, `allow: ["src/checkout/**"]` — а сравнение идёт по префиксу
   (`startsWith(a + "/")`), и `**` читается буквально. Честная правка в `src/checkout/` выходит за
   `allow` → `BLOCKED`, а `protect` с `**` не защищает ничего сверх встроенных масок.
5. **Локальная проверка не видит новых и закоммиченных файлов.** Изменения берутся из
   `git diff --name-status` рабочего дерева. Новый неотслеживаемый файл и правка, которую агент
   успел закоммитить, в `changedFiles` не попадают. Их тест это знает — комментарий в
   `mission-test.mjs`: «The guard reads `git diff --name-status`, which sees tracked edits», — а
   README не говорит.
6. **Старый режим `runcap ci` (без `--mode`) пропускает слабое.** `evaluatePolicyVerdict`
   блокирует только `VERIFIER_COMPROMISED` и `UNVERIFIED`: `VERIFIED_WEAK` даёт `PASS`, пустой
   отчёт `{}` — тоже `PASS`. В `trust-model.md` написано, что `PASS` требует сильной оценки.
   Режим назван «не для слияния», но `action.yml` его по-прежнему предлагает.
7. **Заявление сильнее кода.** В README сказано, что все три слоя сжатия «lossless by
   construction», а `collapseLogBlock` выбрасывает середину лога. Анимация в начале README —
   сценарий из `make-demo-svg.mjs`, а не вывод программы, хотя их же план записи видео
   запрещает «fabricated terminal output». В панели зашит значок «Spend goal: 30-70% less
   waste».
8. **Одно правило в двух местах без договора.** `PROTECTED_GLOBS`, `runShell` и поиск файлов
   проверки скопированы в `adjudicate.mjs` и `mission-control.mjs`. Комментарий обещает «the
   same… so the adjudicator and the local guard agree», но теста на совпадение нет. У cloudflare
   на том же месте тест есть (цикл 4).
9. **Обещанное в плане не выпущено — и это названо.** План Tier 3 требовал
   `INSTALLATION_NOT_HARDENED`, который валит проверку, если защита ветки не подтверждена. В
   0.6.0 его нет, но вердикт честно печатает «не проверялось». Это не дефект, а граница.

## Сверка их классов с нашим кодом

- **Прогонщик, который судит по тексту.** В `tool/` не нашлось ни одного `on("close")`, который
  отбрасывает код возврата; наши проверки берут `status` у `spawnSync`. Сверено поиском.
- **Неизвестное как ноль.** Одно место: `report-html.mjs:108` — время гейта
  `last.secs?.[g] ?? 0` печатается как «0.0 с». Время пишется для каждого запущенного гейта, так
  что ноль достаётся только старым строкам истории. Мелочь, но класс тот же. Кандидат на правку.
- **Судья из кандидата.** Наш `action.yml` запускает `npx agent-quality-kit@$AQK_VERSION`, по
  умолчанию `latest`: плавающая версия, которую наш же `deps-are-pinned` отметил бы у чужого.
  Манифест `.aqk.yml` читается из проверяемого дифа — отсюда находка выше.

## Закрыто 2026-09-26: команда гейта в снимке защиты

Решение владельца — вариант (а), «делаем идеально». Из (б) взята суть: красная строка сама
печатает «было» и «стало», отдельная некрасная строка не понадобилась.

| что | как | чем доказано |
|---|---|---|
| подмена команды при том же имени | снимок `gates-declared.txt` хранит строку `# run имя: команда`; расхождение с манифестом — красное, с «было / стало» | `smoke/protection-command.test.mjs`: подмена, стёртая строка, две строки на гейт, снятый с причиной |
| сквозной сценарий из разбора | `init` → `add` двух гейтов → коммит → команда `secrets-not-in-code` = `"true"` → `doctor --run` | тот же файл, последний тест: код не 0 и назван `protection-not-removed` |
| две копии одного правила (sh и JS) | команду из манифеста гейт читает так же, как `parseManifest`, которой программа её запускает | договорной тест на пяти трудных строках (`c#`, комментарий после пробела, одинарные кавычки, табуляция) с контрольной порчей каждой строки |
| старые снимки у пользователей | без единой строки `# run` — зелёный с советом «подмену не вижу»; `aqk add` любого гейта дописывает строки всем, записанные не трогает | тесты «старый формат» и «`add` не переписывает записанную» |
| наш собственный снимок | переведён на новый формат: 31 команда | гейт на нашем репозитории зелёный, прочитанные sh команды совпали с разбором программы |

Граница, названная вслух в README гейта: кто переписал и команду, и строку `# run`, сделал правку
защиты открыто — её видно в дифе снимка. Проверка требует, чтобы смена была названа, а не чтобы
она была верной. До этой правки README честно говорил «гейт, выхолощенный до `true`, не
ловится» — то есть дыра была записана, но не закрыта.

## Решение за владельцем (на момент открытия)

1. **Как AQK должен реагировать, когда в том же дифе поменялась команда гейта.** Варианты:
   (а) `protection-not-removed` помнит не только имена, но и команды, и смена команды краснеет,
   пока причина не записана рядом — как сейчас со снятием гейта; (б) `doctor --run --since`
   сравнивает манифест с базой и печатает отдельную строку «правила изменены в этом же дифе:
   было… стало…», не роняя прогон; (в) и то и другое.
2. **Прогон их кода** — разрешить в черновой папке, чтобы находки 1–6 стали проверенными, а не
   прочитанными. Писем им не пишем, так же как OCR.
3. **«Красный тест до кода» машиной.** Их приём — прогнать проверку на базе и потребовать
   падения — закрыл бы одно из наших правил с меткой `человек`. Это новая возможность, а каталог
   заморожен (`PROJECT.md` §9а). Записано как кандидат, не делается.
