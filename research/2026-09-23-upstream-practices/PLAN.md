## 1. Закрыть обнаруженный ложный успех AQK

Поведение: отсутствующая база сравнения у `test-not-adjusted` даёт «не удалось проверить»
с ненулевым кодом, а не успешный пропуск.

- Добавить сценарии в `tool/selfcheck/smoke/`: один коммит; неизвестный ref;
  корректный явно заданный ref; доступная история и обычный чистый результат.
- Сначала увидеть красную регрессионную проверку на текущем коде.
- Минимально исправить ветку недоступного ref, затем подтвердить, как её классифицирует раннер.
- Не подменять отсутствие сравнения сравнением с пустым деревом без отдельного решения:
  это изменило бы смысл проверки.
- Арбитры: точечный smoke → проверка затронутого гейта → обязательные проверки проекта.

Входное доказательство: `evidence/missing-base.json`. Это первый предлагаемый кодовый шаг.

## 2. Полностью разобрать четыре основных источника

Пофайловый проход `smixs/code-quality` завершён: 105/105 записей, шесть ограничений
подтверждены изолированными пробами; полный Bun/integration-прогон остаётся в очереди.

Порядок: `smixs/code-quality` → `mattpocock/skills` → `jakubkrehel/skills` → `emilkowalski/skills`.

Для **каждого** файла из `files.tsv`:

1. Прочитать содержимое порциями без обрезки; для бинарного артефакта определить назначение
   и проверить подходящим средством. Сгенерированные файлы и lock-файлы не выдавать за
   новый инженерный приём: проверить происхождение/согласованность, обозначить этот вид проверки.
2. Записать роль файла, зависимые файлы, доказанную/заявленную пользу и ограничения.
3. Сопоставить с конкретным местом AQK: уже есть / можно адаптировать / отдельный профиль /
   не подходит / требуется дополнительная проверка. Отказ содержит причину.
4. Для исполняемых механизмов испытать красный, зелёный и аварийный сценарий в изоляции.
5. Сохранить commit + path + наблюдение. `read` не повышать до «проверено запуском» без лога.

Результат: у каждой записи есть содержательный вывод или явно названная причина, почему она
не требует ручного смыслового разбора. Число необработанных файлов видно в описи и уменьшается.

## 3. Обновить сравнительный корпус защиты тестов и проверок

Зафиксировать версии code-quality, checkwash и AQK. Повторить прежние случаи, добавив границы:

| Группа | Красный случай | Зелёный контроль |
|---|---|---|
| Точное утверждение | `assert.equal` → `assert.ok` | Усиление утверждения |
| Тест удалён | Удаление единственного проверяющего сценария | Перенос/переименование с сохранением поведения |
| Тест выключен | Необоснованный skip | Явно согласованный временный пропуск с учётом в отчёте |
| Запуск обесценен | `npm test || true` | Команда с корректной передачей отказа |
| CI/хук | Ошибка погашена в YAML или shell | Служебный post-hook без приёмочного вердикта |
| История недоступна | Неверная база / shallow history | Корректный диапазон |
| Свидетельство устарело | После прогона изменён код, тест или конфиг | Повторный прогон того же состояния |
| Git index | Проверено дерево, коммитится другая staged-версия | Проверенная версия совпадает с коммитом |

Мерить отдельно пойманные дефекты, ложные блокировки и несостоявшиеся проверки.
Способ переноса выбрать **после** таблицы: штатная интеграция, улучшение upstream,
либо собственная реализация при доказанном пробеле. Внешнее обращение автору — только по поручению.

## 4. Испытать небольшой инженерный набор скиллов

Кандидаты: diagnosing-bugs, tdd, короткие to-spec/to-tickets, двухосевое code-review.
Сначала сверить все их файлы и ссылки; не включать непрочитанные инструкции.

Предлагаемая адаптация:

- Один входной артефакт задачи: желаемое поведение, ограничения, арбитр и критерий завершения.
- Один воспроизводимый результат за изменение.
- Машинные проверки выполняются командами; смысловое ревью отделено от них.
- Исследовательские рекомендации не дают агенту самостоятельного разрешения на публикации,
  коммиты и установку глобальных настроек.
- Дублирующиеся с существующими правилами инструкции заменяются ссылками, а не размножаются.

Пилот: несколько сопоставимых реальных задач AQK, зафиксированные исходные состояния,
одинаковые ограничения и независимые контрольные дефекты. Сохранить время, число возвратов,
непойманные дефекты и цену ручного разбора. Маленький опыт не объявлять статистическим доказательством.

## 5. Разобрать топ-5 и дополнительные проекты по той же описи

Приоритет смыслового чтения: Evalite → Sandcastle → ts-error-translator → ts-reset → dictionary.
Затем тематические проекты, указанные в SOURCES.md, включая книги и небольшие воспроизведения.

Особенно проверить:

- Как Evalite учитывает неуспешные, отсутствующие и повторные оценки.
- Какие изменения Sandcastle переносит из изолированной среды и что считается завершением.
- Сохраняется ли первичная ошибка при переводе в понятное сообщение.
- Где статическая типизация заканчивается и требуется проверка данных в рантайме.
- Какие книжные рекомендации конфликтуют между собой и с задачей небольшого CLI.

Не включать сам оркестратор или LLM-раннер в AQK только потому, что они популярны.
Кандидат на инструмент исследования может быть полезен без превращения в зависимость продукта.

## 6. Измерить недостающие свойства качества AQK

После независимого инструмента измерения рассмотреть отдельные пилоты:

1. Покрытие изменённых строк: отсутствие отчёта, устаревший отчёт и провал тестов не дают зелёного.
2. Настоящая сложность функций: отчёт штатного анализатора, реальные проблемные функции,
   оценка шума. Порог — результат решения, а не автоматический импорт чисел доклада.
3. PBT для одной критической чистой функции: инвариант, независимый ожидаемый результат,
   воспроизводимый seed и уменьшение контрпримера.
4. Mutation testing одного критического модуля: baseline зелёный, мутация кода,
   разделение survivor / killed / tool error. Не требовать 100% без разбора эквивалентных мутантов.

Нулевая runtime-зависимость CLI сохраняется. Возможность внешнего закреплённого инструмента
разработки оценивается отдельно: не маскировать её под «зависимостей вообще нет».

## Когда исследование и перенос можно назвать завершёнными

- В описи не осталось нерассмотренных файлов согласованного корпуса; автоматическая проверка
  сгенерированного артефакта явно отличается от ручного смыслового чтения.
- Каждая рекомендация связана с источником, пробелом AQK и способом измерить результат.
- Согласованные изменения прошли red → green и релевантную приёмку.
- Полезное принято, дубли/неприменимое отклонены с объяснением; «установили всё» не является метрикой.
- Итог называет оставшиеся риски и границы доказательства.
