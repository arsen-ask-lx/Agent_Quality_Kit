## Главный вывод

Наибольшая ожидаемая польза — объединить понятную постановку задачи, воспроизводимую диагностику,
детерминированную проверку и адресное ревью. Установка всех скиллов сама по себе этого не даёт:
инструкции дублируются, спорят между собой и иногда предписывают действия, которые нашему процессу
не нужны. Пользу конкретного заимствования ещё предстоит измерить на задачах AQK.

Текущая особенность AQK — проверять работоспособность защиты и честность её результата.
`code-quality` проверяет свойства изменения, Matt описывает инженерный процесс, Emil и Jakub —
практики интерфейсов. Это разные части процесса, для которых нужны разные способы проверки.

Прежняя заморозка расширений в `PROJECT.md` — контекст прежнего решения. Текущий запрос владельца
открывает пересмотр стратегии; он не является основанием автоматически отклонять полезные идеи.
При этом обещание «лучше всех вместе» пока не имеет измеримого критерия. Предлагаем мерить:
пойманные реальные дефекты, ложные блокировки, время до проверенного исправления и цену сопровождения.

## Что есть в AQK на самом деле

| Практика | Состояние AQK | Что следует из сравнения |
|---|---|---|
| Падающая проверка перед исправлением | Есть в `AGENTS.md` и `kit/rules/testing.md` | Не нужен второй пересказ; полезны конкретные способы построения воспроизведения из diagnosing-bugs |
| Тестирование поведения через интерфейс | Уже описано в `kit/rules/testing.md`; есть units и smoke | Переносить методику выбора наблюдаемого результата, проверяя реальные тесты, а не добавлять лозунг |
| Проверка самого гейта | `prove`, red/green, внешний `evals`, `probe` | Сильная база для оценки заимствований; это не заменяется обычным линтером |
| Пропуск / ошибка / нарушение | Разделены в SPEC и раннере | Найден отдельный нарушающий договор путь в `test-not-adjusted` |
| Проверка подмены тестов | `test-not-adjusted` делегирует checkwash | Сверить текущие версии на едином корпусе подмен, включая законные изменения теста |
| Защита CI и хуков | `ci-actually-fails`, `hook-actually-fires`, другие записи | Сохранить при интеграции code-quality: их область отличается |
| Сложность | Свой подключённый portable-гейт оценивает отступы/вложенность | Это не CC ≤ 10, cognitive ≤ 15 и не CRAP |
| Покрытие изменённых строк | В подключённом манифесте отдельного такого гейта нет | `report --since` учитывает упоминание файлов проверками, не исполнение строк тестами |
| Mutation testing | `mutation.sh` меняет образцы: сдвиг строк и CRLF | Это проверка устойчивости к преобразованиям; мутации исполняемой логики Stryker — другой опыт |
| Property-based testing | Подключённого fast-check/Hypothesis в изученном манифесте и CI не найдено | Пилот на парсере/храповике полезнее требования генераторов для каждого файла |
| Контроль свежести свидетельства | Уже есть `evidenceHash` в `tool/lib/evidence.mjs` | Сначала испытать существующий механизм; не добавлять второй отпечаток без найденного пробела |
| Единый запуск проверок | Уже есть `doctor --run`, группы и jobs | Не нужен второй главный quality-скрипт; сторонний инструмент можно подключать как гейт |
| Интервью → спецификация → небольшие задачи | Методички есть, рабочий контур нужно проверить отдельно | Пилот короткой спецификации и вертикального изменения на реальной задаче |
| Проверка интерфейса | AQK — в основном CLI; отдельный UI-профиль не подключён | UI-скиллы пригодятся соответствующим проектам-получателям и будущему интерфейсу |

Важная оговорка: `kit/docs/ai/quality-gates-checklist.md` уже явно помечен как исторический
снимок **audit_project**, Django + React. Это полезное сырьё, но его галочки нельзя засчитывать
самому AQK. Нового дефекта документации одним этим фактом не установлено.

## Два живых измерения

### 1. Отсутствующий базовый коммит даёт успешный код выхода

Источник: [`kit/gates/test-not-adjusted/check.sh`](../../kit/gates/test-not-adjusted/check.sh),
строки 74–79. Создан временный репозиторий с одним коммитом, затем вызван этот гейт.

Наблюдение: `HEAD~1` не разрешается; сообщение говорит, что сравнение пропущено; **exit code = 0**.
Полный результат — [missing-base.json](evidence/missing-base.json).

Это конфликт с договором SPEC §4: когда сравнение не состоялось, оно не должно выглядеть как
успешная проверка. Следующий шаг — регрессионная smoke-проверка, красная на текущем коде,
затем минимальная правка после согласования плана. checkwash для воспроизведения этого пути
не требуется: возврат происходит раньше вызова инструмента.

### 2. Тридцать последовательных if проходят гейт сложности

Временный `src/classify.js`: одна функция, 30 независимых `if`, один уровень отступа.
`complexity-limit/check.sh` вернул **0**, без находок.

Это **не новый баг**: заголовок скрипта прямо говорит, что он меряет вложенность и не заменяет
цикломатическую сложность. Проба показывает, почему нельзя поставить галочку «сложность из
доклада уже закрыта». Полный результат — [flat-branches.json](evidence/flat-branches.json).

### Sergey Shima: code-quality

В AQK уже есть [предыдущий разбор](../competitors/code-quality-skill.md) другого коммита.
Он ценен как старый эксперимент; его результаты нельзя объявлять новым прогоном.
Текущий снимок — `407501608b` из `smixs/code-quality`.

Полезные механизмы из прочитанного кода:

- `scripts/lib/tamper.ts` содержит распознавание ослабления `assert.equal/strictEqual/...`
  до `assert.ok`/truthy, пропуска и удаления теста, вмешательства в baseline.
  Это источник **случаев для сравнения**, а не повод скопировать ещё один распознаватель без замера.
- `scripts/lib/crap.ts` связывает повторное использование coverage с отпечатком исходников.
  Для AQK отдельно проверить тесты и конфигурацию как входы свидетельства; собственный
  механизм отпечатка у нас уже существует.
- `scripts/lib/hooks.ts` отказывает при одновременных staged/unstaged правках одного файла,
  поскольку анализирует рабочее дерево. Это конкретная проверка того, какое состояние оценено.
- Один механизм вызывается разными адаптерами агента и хуками. У AQK аналогичная архитектурная
  цель уже реализована через CLI: интеграция должна использовать её.

Ограничения текущего снимка:

- [Средний CRAP](https://github.com/smixs/code-quality/blob/407501608b1ffe8ab0e236b742513592fca9ed60/scripts/lib/gate.ts#L133)
  диагностический, превышение среднего само по себе не блокирует. Это отличается от чтения
  слайда как универсального жёсткого порога.
- `gate.ts` сохраняет отдельную ветку docs-only для md/toml/json/yaml вне `project.src`.
  Наличие `tamperCheck` в этой ветке видно; проверку всех путей выключения CI она этим не доказывает.
  Старый сравнительный эксперимент требуется повторить на новой версии.
- Уточнение второго прохода: тезис `limits.md` о неработающем первом коммите расходится с
  `diff.ts`, `hook-chain.md` и тестом `pipeline.test.ts:135`. Это расхождение документации;
  прежний пересказ не является подтверждённым отказом хуков. Полный coverage-run — иной путь.
  Неполный отбор тестов и optional/not-run инструменты подтверждены исходниками и тестами.
- Bun, анализаторы и их загрузка — эксплуатационная цена, даже когда package.json не содержит
  обычного списка runtime dependencies. Полный Bun-набор не запускался, плагин не установлен. Во втором проходе выполнены
  13 независимых наблюдений над экспортированными функциями под Node; границы в новом разборе.

Вывод: сначала общий корпус и опыт интеграции отдельным гейтом; полное встраивание пока не обосновано.

### Jakub Krehel: проверка интерфейса и честность отчёта

Наиболее переносимая идея для AQK — формат отчёта:
**область → осмотренное доказательство → результат → непроверенное → конкретное действие**.
`better-interface/review-format.md` различает проверенную чистую область и нерассмотренную.
AQK уже различает состояния запуска; полезно сохранить такую же точность в смысловом ревью.

`break` предлагает испытать настоящий компонент на применимых состояниях с реальными стилями,
а затем сообщить наблюдавшиеся поломки. Это кандидат для UI-профиля проектов-получателей.
Ограничение «один взгляд» — бюджет автора, не достаточное доказательство исправности.

`better-accessibility` содержит проверяемые вещи: управление клавиатурой, имена элементов,
фокус, размер целей, масштабирование. Отдельные требования сверены с W3C: например,
[WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) задаёт
24×24 CSS px с исключениями. Рекомендация делать touch-цели 44×44 — иной уровень рекомендации.
Автоматическая проверка не доказывает полную доступность всего интерфейса.

## Какие утверждения действительно подтверждены внешними первоисточниками

| Утверждение | Проверка | Решение |
|---|---|---|
| Red → green → refactor | [Fowler: TDD](https://martinfowler.com/bliki/TestDrivenDevelopment.html) | Основа процесса, а не обещание отсутствия багов |
| Покрытие 80% достаточно всем | [Google Testing Blog](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html) прямо отвергает универсальное идеальное число | Порог выбирать по риску и замеру; дополнять проверкой способности тестов ловить брак |
| Cognitive complexity 15 — универсальная граница | [Ответ разработчика Sonar](https://community.sonarsource.com/t/s3776-reason-for-the-current-default-value-of-15/127103): эмпирический выбор, для C/C++ другой порог | Начальное значение инструмента, не закон качества |
| Мутации показывают чувствительность тестов | [Stryker](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/) различает killed, survived, no coverage, ошибки | Не считать ошибки инструмента пойманным дефектом; начать с критического модуля |
| PBT даёт другие контрпримеры | [fast-check](https://fast-check.dev/docs/introduction/why-property-based/) описывает генерацию, shrinking и воспроизведение seed | Пилот на конкретном инварианте, не случайные данные ради количества |
| Трейсы заменяют логи | [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/) определяет несколько видов сигналов | Трейсы, логи и метрики дополняют друг друга; объём событий зависит от системы |

Состав из конкретных моделей, обязательные два приёмщика на любой задаче, прогулка 15–60 минут,
CRAP < 5 для любого проекта и размер событий 10–100 МБ/день не получили в этом исследовании
подтверждения как универсальные требования. Это рабочие решения спикера или кандидаты на опыт.

Исходных фотографий в этой задаче нет. Пересказ доклада не считается проверенной расшифровкой.
Адрес слайдов не открылся через веб-инструмент; спорные названия сверялись по репозиториям.
`grilling with docs` соответствует нынешнему `grill-with-docs`, а `pocock-code-review` —
ближайшему по смыслу нынешнему `code-review`. `gauntlet`, `humanizer-ru`, `autograph`, медиа-скиллы
и `shadcn` не подтверждены как элементы четырёх основных снимков; выдуманных ссылок на них нет.
