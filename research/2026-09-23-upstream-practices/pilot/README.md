# Пилот измерения: четыре прибора по одному модулю

Пункт 3 остатка [цикла 1](../CYCLE-01.md), замер 2026-09-26. Node 22.23.0, Linux/WSL,
eslint 10.10.0. Модуль — `tool/lib/execution.mjs` (147 строк): он решает, что считать находкой,
что сбоем инструмента, а что чистым результатом. Выбран не по размеру: если его проверки не ловят
подмену этого решения, не ловит ничего и всё, что стоит выше — `prove`, `doctor --run`, ступень,
значок.

Порядок — из свода: **прибор раньше улучшений**. Сначала измерить, потом говорить о порогах,
потому что порог без замера — это наш вкус, выданный за стандарт.

## 1. Покрытие: встроенный в Node, без зависимостей

`node --test --experimental-test-coverage tool/selfcheck/units*.mjs`

| Что | Строки | Ветви | Функции |
|---|---:|---:|---:|
| `execution.mjs` | 97.28 % | 93.75 % | 90.00 % |
| весь проект | 84.65 % | 91.87 % | 55.72 % |

Непокрыто в модуле: строки 142–145 — кеш поиска Git Bash, который на Linux не вызывается.

**Вывод.** Прибор есть и стоит ноль: зависимостей не нужно, прогон тот же. Числу по проекту
(55.72 % функций) верить как цели нельзя — это закон Гудхарта в готовом виде, и в проекте с
двумя десятками команд низкое покрытие функций говорит о том, что команды проверяются прогоном
на чистой папке, а не модульно. Покрытие ИЗМЕНЁННЫХ строк было бы осмысленнее, но это уже
продуктовая команда, а не замер: решение о ней — отдельно.

## 2. Настоящая сложность против нашей переносимой — главное число пилота

| Прибор | Находок в `tool/` |
|---|---:|
| наша переносимая проверка (вложенность по отступам) | **0** |
| `eslint --rule complexity:10, max-depth:4` | **52 + 6** |

Распределение цикломатической сложности: `11–15` — 23, `16–25` — 20, `26–50` — 7, **`>50` — 2**.

Худшие: `cmdDoctor` **85**, `runGates` **60**, `cmdReport` 50, `reportCatalog` 48, `cmdVitals` 38.

**Почему ноль против пятидесяти двух.** Переносимая проверка меряет ГЛУБИНУ ОТСТУПА, а наш код
написан плоско — ранние возвраты, никакой вложенности. Ветвлений при этом десятки, и они лежат
на одном уровне. То есть прибор мерит не тот признак, а не «мерит мягче»: между 0 и 52 нет
порога, при котором они сойдутся.

Это подтверждает запись, стоявшую в `PLAN.md` как предположение («не считать portable-вложенность
CC»), — теперь она замер. И это признание про нас самих: наш манифест объявляет
`complexity-limit`, а рецепт под него не видит класса, про который запись написана.

**Порог не назначен намеренно.** Из 52 находок 23 лежат в `11–15` — для функции команды CLI это
спор о вкусе, и список из 52 пунктов на первый день не разбирают, а закрывают. Развилка
(решение владельца, не агента): `npx --yes eslint` под храповиком с реестром текущих 52 и целью
по худшему хвосту — против того, что в манифесте прямо записано «готовых инструментов
(ruff, eslint) в этом репозитории нет и не будет». Прецедент есть: `dead-code` уже зовёт
`npx --yes knip@6`, и зависимостью в `package.json` он не стал.

## 3. Мутационная проверка модуля: 12 мутантов по смыслу

`node research/2026-09-23-upstream-practices/pilot/mutate-execution.mjs`

| Исход | Сколько |
|---|---:|
| убит адресными проверками модуля | 11 |
| убит только общим набором | 0 |
| **ВЫЖИЛ** | **0** |
| эквивалентный (поведением не убить) | 1 |

Отличие от `tool/selfcheck/mutation.sh`: тот меняет ОБРАЗЕЦ и требует, чтобы вердикт НЕ изменился;
здесь меняется КОД и требуется, чтобы проверки заметили. Второго вопроса у комплекта не было
ни для одного модуля.

**Эквивалентный мутант разобран, а не списан в успех.** `pylint: code < 32` сделал бы чистый
прогон находкой — но `classify` возвращает «чисто» на нуле ДО обращения к адаптеру, а
`findingCodes` вызывается только аргументом `classify` (проверены все три места: `prove.mjs`,
`gates.mjs`, `run.mjs`). Поведением его не убить; требовать 100 % значило бы дописать проверку
формы записи условия вместо проверки продукта.

**Что пилот дал продукту.** Разбор этого мутанта показал, что утверждения были только про
НЕНУЛЕВЫЕ коды: половина таблицы каждого адаптера не проверялась вовсе. Добавлено утверждение
«ноль — чисто» для всех шести адаптеров. Мутанта оно не убивает (он эквивалентный), и выдавать
это за убийство нельзя — оно закрывает пробел в договоре, который заметен только так.

## 4. Свойства на случайных входах: 11 000 входов, два зерна

`tool/selfcheck/units-execution-props.mjs` — подхватывается гейтом `units` по маске `units*.mjs`.

Без библиотеки: зависимостей нет, а область значений входа мала. Взамен написано руками то, что
`fast-check` даёт даром, и без чего свойство не свойство — воспроизводимое зерно в коде (не из
часов), НЕЗАВИСИМЫЙ ожидаемый ответ (выведен из шапки модуля, а не списан с её тела) и
уменьшение контрпримера.

Четыре свойства: соответствие независимому ожиданию; ровно три состояния и ни одного больше;
у сбоя всегда названа причина, у остальных её нет; одинаковый вход — одинаковый ответ.

**Контрпримеров не найдено.** Это результат, а не пустота: функция мелкая и уже покрыта
названными случаями. Прибор при этом доказан красным — подмена `if (code === 0)` роняет свойство,
и уменьшение печатает минимальный вход
`{"tool":"несуществующий","signal":null,"error":null,"status":0}`. Прогон — 103 мс.

## Что пилот решил, а что оставил решать

| Прибор | Цена | Нашёл | Решение |
|---|---|---|---|
| покрытие | ноль, встроено | пробел в 4 строках | оставляем как замер, целью не делаем |
| настоящая сложность | `npx`, сеть | **52 против 0** | развилка владельцу: храповик или признание в записи |
| мутации модуля | скрипт на 100 строк | пробел в договоре адаптеров | закрыто утверждением |
| свойства | 103 мс, без зависимостей | ничего | оставляем: дешевле, чем повод его снять |

Остаток пункта 3: покрытие ИЗМЕНЁННЫХ строк (отсутствие отчёта, устаревший отчёт и провал тестов
не должны давать зелёного). Прибор в Node есть и без зависимостей, но это продуктовая команда,
а горизонтальные возможности заморожены решением 2026-09-10 — открывается замером пользы, а не
желанием.
